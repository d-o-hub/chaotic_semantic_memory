## Why #754 is (mostly) a no-op

Counting global allocator, `rustc -O`, identical work, 3 runs, byte-stable
results, n = 256 items (throwaway probe):

| hunk | site | old (allocs / bytes) | new (allocs / bytes) | verdict |
|---|---|---|---|---|
| 1 | `graph_candidates` HashSet | 8 / 9 308 B growth from `new()` | 1 up-front reservation | real but tiny; over-allocates when the frontier ≪ `max_candidates` |
| 2 | `graph_candidates` tail | 347 / 28 222 B | 341 / 16 126 B | **self-contradicting**: `with_capacity(len.min(max))` then pushes all `len` items → reallocates exactly when `len > max_candidates`, the case the comment claims to fix |
| 3 | `score_specific_candidates` | 347 / 28 222 B | 341 / 16 126 B | minor growth-chain delta; "iterator closure invocation overhead" is wrong — adapters inline away in release |
| 4 | `exact_similarity_scan` + second scan tails (×2) | 257 / 11 264 B | 257 / 11 264 B | **zero delta** — `.map()` over `vec::IntoIter` is `TrustedLen`; `collect()` already allocates exactly once at `len` |

Closing reasons:
1. Two of five hunks provably zero-delta (hunk 4, both scan tails).
2. The remaining ~13 allocs / ~12 KB growth-chain bytes per query sit next to
   257 unavoidable `String` clones (11 KB) and 256 `hamming_distance` scans over
   1 280-byte vectors — the code the PR keeps (`id.clone()`,
   `concept_indices[idx].clone()`) dominates the churn it claims to remove.
3. Hunk 2 contradicts its own goal (table above).
4. No criterion output or flamegraph attached → not review-ready under the
   ADR-0095 perf-evidence bar.

The added `test_score_specific_candidates_behavior` is a reasonable behavior
test but is not what the PR claims to deliver.

## What a real fix would look like

Carry `usize` indices to the API boundary instead of materialising
`(String, f32)` pairs with clones at every hop (257 allocs → ~1 per query), or
return borrowed/`Arc<str>` ids. Any resubmission must beat the criterion
baselines in `plans/evidence/scale_release_2026_09_21` with attached numbers.
