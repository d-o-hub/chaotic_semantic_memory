## #783 — closed with no demonstrated zero-fill-elimination benefit

Premise: replacing zero-initialized arrays with `MaybeUninit` in
`crates/csm-core-lib/src/hyperdim_binary.rs` removes 1 280-byte zero-fills
before `copy_nonoverlapping`, claiming ~3.7% on `bhvec_to_bytes` and ~0.8% on
`bhvec_from_bytes`.

Disassembly adjudication (x86_64, rustc 1.98.1, `-O -C codegen-units=1`,
`#[no_mangle] #[inline(never)]` variants linked into one binary):

- `from_hvec` old/new and `from_bytes` old/new fold to the **same address**
  (`nm`: both symbols at one address) — byte-identical code.
- An **old-only** build disassembles to a bare `memcpy` call: LLVM already
  dead-store-eliminates the `[0u64; 160]` initializer because the full-width
  copy overwrites it. There is no zero-fill left to remove.
- `to_bytes` old/new emit the same `alloc(1280)` + `memcpy(1280)` sequence and
  differ only in instruction scheduling (len/cap stores placed around the
  memcpy). No `memset` in either body.
- This rules out the claimed zero-fill-elimination mechanism in the inspected
  builds, not every possible timing effect: `to_bytes` has a real instruction
  scheduling change. Its claimed ~3.7% needs reproducible benchmark evidence;
  disassembly alone does not establish that all reported deltas are noise.

Gate/process state: the `commitlint` job failed on the perf-evidence gate
(annotation: missing `## Performance Evidence` in the PR body); commit 1's
`perf(core-lib)` scope is not in `commitlint.config.cjs` `scope-enum`
(`hyperdim_binary` is); the PR is a draft and BEHIND `main`.

Closure: roast comment posted, PR closed as no-op. The supported finding is
narrower: no demonstrated zero-fill-elimination benefit in the inspected
builds, not a blanket zero-codegen-delta verdict. A resubmission claiming a
scheduling benefit must provide reproducible affected-path benchmarks rather
than attribute it to an absent zero-fill. Repro: compile each variant
`#[no_mangle] #[inline(never)]`, link, `objdump -d`; the old-only variant shows
only `memcpy`.
