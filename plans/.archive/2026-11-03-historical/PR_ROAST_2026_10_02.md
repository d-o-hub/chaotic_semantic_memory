### #807 — what the evidence gate and the body did not catch

The `feat:` title bypassed `scripts/check-perf-pr-evidence.py` entirely (`if not title.startswith("perf("): return 0`) while the body carried a ~6.4x headline. The number was checked by hand instead and does not hold:

- **A provably false documented invariant.** `complex_quadratic.rs:34-41` wraps each coordinate with `(v % 2.0) - 1.0` and the body calls the result `[-1.0, 1.0]`. Rust's `f64 % f64` is IEEE remainder with the sign of the dividend, so the reachable set is `(-3.0, 1.0)` (`v = -2.5` → `-1.5`). No simulation needed — the fmod sign rule is enough. It is also a per-coordinate wrap, not a fold of `|z|`, so the code is not the complex quadratic map whenever the branch fires.
- **No key, no hash.** `next_value(&mut self)` (`:48`) takes no input and produces no digest; `ChaoticLsh::new` hard-codes `Slhm2d` (`chaotic_lsh.rs:21-27`) and `grep -r ComplexQuadraticMap` finds zero callers repo-wide. The body's "fits securely into the existing LSH project semantics" has nothing behind it.
- **Bench blind by its arguments (the #800 class).** `c = -0.8 + 0.156i` is outside the main cardioid (`1 − sqrt(1−4c)` has modulus 1.066 > 1), so the orbit escapes and the `%` libcall sits on the hot path — while the body claims seeds "chosen near the Mandelbrot set boundary". The measured ratio therefore depends on a branch the prose never mentions. The *stated cause* is true (`Slhm2d::next` calls `libm::sin` twice per iteration, `hyperchaotic.rs:33-34`) and the harness is structurally comparable (same criterion group, same `b.iter`/`black_box` body, one iteration per arm) — that part is to the author's credit; the magnitude is not established.
- **The table self-contradicts.** Both rows read "Verified" for entropy while quality reads "Not measured", and the only distribution test is 20 000 samples into 10 buckets asserting `count > 0` (`:100-110`) — true of any stream producing 10 distinct values. The baseline row's "Verified" rests on the same class of test (`hyperchaotic.rs:94-104`).
- **Coverage regressed against its own prior submission.** #768 had `test_complex_quadratic_determinism`; #807 dropped it, while `hyperchaotic_chebyshev.rs:91-103` and `neural_circuit.rs:78` both keep one.
- **Citation:** Crossref `10.1016/j.chaos.2023.113647` resolves and matches the body's title/authors/journal (Ayubi, Setayeshi, Rahmani, *Chaos Solitons Fractals* 173, 2023). Full text is 403 at ScienceDirect, ResearchGate, ADS, Scilit and Bohrium, so the algorithm cannot be line-checked — which is exactly what the unretired `[FALLBACK]` marker says. The paper's contribution per the abstract is a *generalized* complex map used as a keyed hash with a key space, plus statistical/collision/key-space/speed analyses; the PR ships none of it.

### #808 — the perf claim is refuted by measurement, not by opinion

The prior round's blockers were genuinely resolved: SAFETY/rationale comments restored (`SAFETY` occurrences in `hyperdim_simd.rs` 22 → 26), the `MaybeUninit` + `get_unchecked` fallback replaced by the safe `xor_u64_scalar` oracle, four parity tests pinning the kernels against that oracle on head/tail words and across the `BHVec`/`HVec` layouts, and the dispatch extracted next to the identical `hamming_distance_u64` dispatcher rather than by deleting comments to fit the 500-line gate. All of that is correct and independently verifiable.

The 1.7–2.0× claim is not. The PR's own bench is not blind — `bhvec_bind` calls the changed `BHVec10240::xor` directly — so it was measured, same host, alternating arms:

| arm | mean | CI |
|---|---:|---|
| `main` `47a7457`, scalar loop (`bhvec_bind_baseline_main`) | **89.5 ns** | 87.2 – 91.9 |
| #808 SIMD dispatch (`bhvec_bind`) | **113.3 ns** | 110.2 – 116.8 |

Non-overlapping intervals; rustc 1.88.0, release profile, Intel i5-8350U with AVX2 present, so the dispatched path is the one timed. The body's 287.6 ns → 141.5 ns does not reproduce and the sign inverts.

**Root cause, from `--emit asm`.** `xor_u64` is `#[inline]`, so the body now inlines into `xor` as:

```
sub  rsp, 1288                     ; 1,280-byte stack buffer
mov  rax, [rip + std_detect cache]  ; runtime AVX2 detection
...  js .LBB175_5
.LBB175_3:  call memset            ; zeroes the whole buffer
.LBB175_4:  160-iteration scalar xor loop into rsp+8
.LBB175_5:  call xor_simd_u64_avx2 ; real call, not inlined
.LBB175_6:  call memcpy            ; 1,280 bytes back to the return slot
```

Three costs the old body does not have:

1. **`memset` of 1,280 bytes** — the `[0u64; 160]` stack temporary now lives across the `MaybeUninit`-writing kernel call, so it must be pre-zeroed. `main`'s body has no `memset`.
2. **`memcpy` of 1,280 bytes** out of the return slot (also on `main`, so not new) — but now the kernel's argument *and* result are both stack buffers.
3. **The AVX2 kernel cannot inline.** `xor_simd_u64_avx2` is `#[inline]` *and* `#[target_feature(enable = "avx2")]`; a `#[target_feature]` fn cannot be inlined into a caller lacking the feature, so it is an out-of-line `call`. Its own 40 × `vmovups`/`vxorps` loop over `ymm` is fine — it writes into the pre-zeroed stack buffer that is then `memcpy`'d out. The data crosses the stack **three** times instead of once.

**The premise is wrong for this compiler too.** The body says LLVM "leaves scalar" on the old loop, citing "the inspected x86_64/rustc 1.98.1 builds" — the workspace MSRV is **1.88** (`Cargo.toml` `rust-version`), so the claim was never checked against the compiler the crate ships with. On 1.88 the old loop is a 160-iteration load/xor/store at 89 ns for 1,280 bytes (~14 GB/s on a 1.70 GHz U-series core). That shape is already bandwidth-bound; a hand-written kernel cannot win it, and adding a stack round-trip loses.

**Why close rather than request changes:** the entire claim is the speedup, and it is refuted by a wider-margin measurement than the one offered. Rubric: "an *after* that is *worse* is evidence against the claim". The residual good work does not depend on the claim and can land separately.

**If pursued later, the evidence points away from more SIMD and at the stack round-trip:** return the kernel output without `MaybeUninit` + `memcpy` (an accumulator in the dispatcher, or `ptr::read` to elide `assume_init`); add a fused `#[target_feature] unsafe fn xor_into(out: &mut BHVec10240, lhs, rhs)` that writes straight to the destination; then measure. If it is still ~89 ns, the correct conclusion is that `main`'s loop was already optimal at this dimension and no SIMD change is warranted — a legitimate, recordable result.

Also recorded: no in-repo hot path calls it (`grep` for `BHVec10240::xor` on the binary type finds only `crates/csm-core-lib/src/hyperdim_binary_tests.rs:14`), so even the original claim bought nothing on any product path.

## Lesson distilled

`progress/LEARNINGS.md`, seven entries: a `feat:` title with a speed claim in the body bypasses the `perf(...)` evidence gate entirely — the gate's scope rule is the kind of thing a review has to notice, because every green check in that case is green for the wrong reason; `#[allow(dead_code)]` on a `pub` item is not a reachability signal; the clamped builder can be the bypassed one; verify a regression test by reverting the fix rather than reading the assertion; a mod fold in a numeric map needs its reachable range proven from the operator's sign rule; bench arguments are membership in an invariant set, not incidental; and a body that cites its *own new* bench is checkable, so measure it rather than reading the table.

Two lessons go to the skill rather than here:

- **Measure the baseline yourself before accepting any perf pair.** #808's 287.6 ns baseline did not reproduce (89.5 ns measured), and the sign of the claim inverted. Copy the cited bench into a worktree on `origin/main` and run both arms on the same host — cheaper than reading, and the only way to catch a number that is true for the author's toolchain and false for the compiler the crate ships with (its premise cited rustc 1.98.1 against an MSRV of 1.88).
- **`#[target_feature]` SIMD into a stack buffer can lose to the scalar loop it replaced.** Disassemble when a "faster" kernel is claimed: a `memset` of the destination, a `memcpy` out of it, and an out-of-line `call` to the `target_feature` fn are three costs a plain `[0u64; 160]` loop never pays. A vectorized kernel only wins when it writes straight to the destination.
