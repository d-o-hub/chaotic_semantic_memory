## #917 — `perf(retrieval): sort query term postings by length ascending`

Draft Jules PR, head `34b9c2ac` (contained `origin/main`), +6/-0 in
`crates/csm-retrieval/src/bm25.rs`. 29 checks passed, `commitlint` failed. Closed with
<https://github.com/d-o-hub/chaotic_semantic_memory/pull/917#issuecomment-6265219919>;
branch deleted.

**1 — Gate.** `scripts/check-perf-pr-evidence.py` rejects a `perf(retrieval)` title with no
`## Performance Evidence` section. The body claimed "warms CPU L1/L2 data caches … improves cache
locality" and carried no numbers. Seventh member of the #737/#739/#740/#754/#783/#800/#915 class.

**2 — The cited comparator cannot see the change.** The branch is reached (`query_weights.len() > 1`
holds on both bench targets), but every bm25 corpus in the repository has **uniform posting
lengths**, so `sort_unstable_by_key` swaps nothing:

- `benches/benchmark.rs:711-719` — query `["memory", "semantic"]`, every document indexed with all
  four tokens ⇒ both postings are exactly `doc_count`.
- `benches/bm25_benchmark.rs:19-29` — doc `i` gets token `j` iff `(i + j) % 2 == 0` ⇒ each of the ten
  tokens lands in exactly 500 documents; the 3-term query has three equal lengths.
- `selective_100000` — term index `(7i + 13j) mod 1000` ⇒ exactly 2 000 postings per term.

This is the #909/#891 blindness class with a new cause: not an unreachable fast path and not the
wrong arguments, but a **flat corpus**. A bench that executes the changed line still proves nothing
when the line is a no-op on that input.

**3 — Measured in its own best case, it loses.** A purpose-built corpus (20 000 docs; postings
20 000 / 2 000 / 200; query supplied in descending length order so the sort reverses it) was run
with the change compiled into two separate binaries and executed **time-interleaved, no rebuild
between**, so thermal/load drift hits both arms equally:

| rep | `csm-retrieval` without sort (µs) | with sort (µs) | Δ |
|----:|----------------------------------:|---------------:|--:|
| 1 | 166.16 | 181.16 | +9.0 % |
| 2 | 170.48 | 179.22 | +5.1 % |
| 3 | 163.47 | 179.95 | +10.1 % |
| 4 | 168.45 | 180.61 | +7.2 % |

Median 168.3 → 180.0 µs, **+8 %**, consistent sign in all four pairs. A fifth single-rep pair after
rebuilding the harness read 171.57 vs 215.72 µs — same direction.

The pre-control pair was misleading and is recorded as such: the first reads were 190 µs (sort)
against 255 µs (no sort), a fake 25 % *win*, taken across a rebuild while load fell. Absolute times
on this host moved ~50 % during the session and the canonical `bm25_search/search_1000_docs`
A/B/A/B sign-flipped (11.59 / 10.87 / 11.81 / 14.82 µs). **On `csm-ref-01` a single A-then-B pair is
not evidence at all**; only the interleaved form is.

Mechanism check agrees with the sign: `bm25.rs:313-334` streams each `entries` slice sequentially
(prefetcher-friendly in any order) while the read-modify-write on `doc_scores[doc_idx]` and
`factors[doc_idx]` is driven by the posting list's own doc indices. Reordering the *term* loop never
clusters `doc_idx`, so the working set is unchanged; rare-first just scatters writes into lines the
dominant pass reloads.

**4 — Correctness: no objection.** The obvious objection was tested and did not hold, so it is
recorded as a non-finding. Scores were bit-identical (`to_bits() = 1084339543`) on the skewed
corpus, and a tie corpus built to expose the unstable-sort dependency (`alpha` 2 000 / `beta` 2 000
/ `gamma` 1 000, `top_k` = 5 cutting through 1 000 exactly-tied docs) returned the same
`doc_0, doc_2, doc_4, doc_6, doc_8` with identical bits in both arms. Reordering `touched_indices`
*is* a latent hazard — it is the input order to `select_nth_unstable_by` + `sort_unstable_by` at
`bm25.rs:342-361` — but no observable difference could be produced.

**5 — Disposition and bar for a resubmission.** Correct, unmeasured, invisible on the repo's
benchmarks, and a measured regression where it engages. A resubmission must carry: a benchmark with
genuinely unequal posting lengths **committed to the repo**; interleaved A/B/A/B from two binaries
with a consistent sign and the load stated; a number that beats +8 % against, not merely differs;
and a parity test locking top-k tie selection.
