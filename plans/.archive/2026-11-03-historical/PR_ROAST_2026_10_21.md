## #927 — `perf(encoder): add zero-allocation fast-path for single-token text encoding`

Jules PR, head `c6e93348`, base `ee4fb2d7` (= current `main`, no rebase needed), `mergeable:
MERGEABLE`, one file: `crates/csm-core-lib/src/encoder.rs` (+18/−8), **no test**. CI red on two
independent counts: `commitlint` → `perf PR evidence gate: missing '## Performance Evidence' section`,
and the repo-wide `Cargo Deny`. Closed with
<https://github.com/d-o-hub/chaotic_semantic_memory/pull/927#issuecomment-6311407717>
(+ <https://github.com/d-o-hub/chaotic_semantic_memory/pull/927#issuecomment-6311501121> control run,
+ <https://github.com/d-o-hub/chaotic_semantic_memory/pull/927#issuecomment-6311563387> correction).

**1 — `main` already short-circuits this.** `encoder.rs:241` returns
`token_to_hvec(tokens[0])` for `tokens.len() == 1 && ngram_size.is_none()`. The PR's guard moves
that decision above `split_whitespace().collect()`, so its entire delta is **one 64-byte
allocation** — which is exactly what #889 recorded as the surviving cost after the earlier work
("1 alloc / 64 B … the surviving 64 B is the token `Vec<&str>`"). The 64 B corroborates the
mechanism: a 1-element `Vec<&str>` takes the minimum capacity of 4, and `&str` is 16 B.

**2 — The `with_capacity` hunk is a re-file of a measured, rejected no-op in this same file.**
`progress/LEARNINGS.md:159` (PR **#776**, 2026-09-25): `tokens.iter().enumerate().map(...).collect()`
is `ExactSizeIterator`-specialized, both forms `1 alloc / n × 1 280 B` at n = 1/3/10, "**Expect this
hunk in most 'avoid intermediate allocations' bot PRs**". #889 carried it; `plans/PR_ROAST_2026_10_15.md`
repair 1 ordered it dropped; its successor **#897** (merged, `c8bd6a51`) landed the fast path *only*
and says so in its commit message. So this half does not come back as a second PR — it is deleted.
Same finding lineage: #706, #739, #740, #754.

**3 — Measured, but the instrument cannot resolve the claim.** Both arms pre-built in separate
worktrees, then interleaved with no rebuild between legs, `/proc/loadavg` per leg:

| pair | `encode_single_1tok` base → PR (ns) | Δ | `encode_batch_5docs` base → PR (µs) | Δ |
|---|---|---|---|---|
| 1 | 654.04 → 662.07 | **+8.0** | 27.091 → 27.456 | +0.365 |
| 2 | 645.93 → 627.27 | −18.7 | 26.409 → 27.651 | +1.242 |
| 3 | 659.23 → 641.64 | −17.6 | 27.253 → 27.811 | +0.558 |
| 4 | 665.46 → 642.46 | −23.0 | 27.992 → 28.298 | +0.306 |
| 5 | 670.82 → 620.96 | −49.9 | 28.066 → 28.123 | +0.057 |

Arm means in a second block (`B B P P B B P P`): base 647.41 ns vs PR 618.51 ns, −28.9 ns.

**Unchanged-arm control (the gap the protocol warns about):** repeats of the *same* binary spread
3.4 ns and **41.1 ns** on `encode_single_1tok`, and 0.93 µs on `encode_batch_5docs`. The host floor
is therefore wider than the mean effect (−23.8 ns), so no single pair proves anything and the
~4–6 % magnitude is not verifiable on this box. Consequences:
- The **batch finding survives**: 6/6 pairs slower is ≈1/64 under a random-sign null, and a wide
  floor does not manufacture a consistent direction. Mechanism is independent — every multi-token
  input now scans `split_whitespace()` in the guard *and* again in the `collect()` below it.
- The **single-token sign** was 5/6; the honest statement is that this instrument cannot resolve the
  magnitude, not that the direction is refuted.
- The body's absolute pair (684 → 638) matches a host in *this* class, not the reference —
  unreproducible for anyone working from `plans/evidence/`.

**4 — Withdrawn charge.** My first comment called "zero-allocation" a misnomer on the grounds that
`HVec10240::new_seeded` allocates 1 280 bytes. It does not: `pub struct HVec10240 { pub data:
[u128; 80] }` (`hyperdim.rs:39`) is an inline array returned by value — stack, no heap. The title is
accurate for already-lowercase input. One caveat that *is* real: the guard sits after
`to_lowercase_cow`, which yields `Cow::Owned` when the text has an uppercase char, so the fast path
is not allocation-free in general.

**5 — What the evidence must be.** The guard and the pre-existing branch return identical values, so
**no behavioural test can distinguish them** — #897's landed tests (`encoder.rs:423`, `:438`) kill
the `tokens.len() == 1` mutant and stay green whether this guard exists or not. The admissible
evidence is an allocation count (`1 alloc / 64 B → 0 allocs`) via the counting-`GlobalAlloc`
protocol. Compounding it: `scripts/mutation_test.sh` scores `--lib` for `csm-retrieval` +
`chaotic_semantic_memory` only, so `csm-core-lib` is outside the mutation gate and CI cannot see the
gap either.

**6 — `p < 0.05` has no source.** Criterion fits a least-squares slope per benchmark with a
confidence interval; it emits no two-sample p-value against a baseline.

**7 — Reachability was fine.** `encode_single_1tok` encodes `"hello"` through `TextEncoder::new()`
(`ngram_size: None`, `code_aware: false`), so the guard does fire — this is not the #763/#909/#891
bench-blindness class. Correctness was never in doubt; impact and admissibility are the issue.

  they fail `EDQUOT` / `disk I/O error` / guard rejection while testing nothing. They now use the crate's
  `NamedTempFile` idiom inside the working directory, which also ends the cross-checkout scratch-database
  collision.
- **Five integration tests pinned contracts the wave had already replaced** — and replaced *in the lib
  target*, where `src/framework_ops_import_tests.rs` already asserts the new semantics, which is why a
  `--lib`-only run looked clean: `framework_import_skips_orphan_associations_without_failing`,
  `import_json_with_associations_to_nonexistent_concepts`, `import_json_skips_invalid_association`,
  `backup_without_persistence_is_ok`, `restore_without_persistence_is_ok`. A replacement import is now
  transactional (a missing endpoint rejects with `NotFound{entity: Concept}`, an out-of-range strength with
  `InvalidInput{field: strength}`, each leaving the store untouched) and `backup`/`restore` without
  persistence return `UnsupportedOperation`. The tests assert the reported entity, id, field and offending
  value, so a future relaxation fails on the reason rather than on a bare error match.
- **This branch's own CLI test called a flag that never existed** — `csm query --format json`, exit 2 with
  clap's "a similar argument exists: `--compact`". `--format` belongs to export/import; `query` reads the
  global `--output-format` (`src/cli/args.rs:32`). The fix was the test, not the surface.

**Verdict on my own work:** the merge's "both sides' tests still pass" claim was made from a *partial* run
(`SCRIPT_CATALOG` drift aborted `validate.sh` before the suite), which is precisely the failure mode the
2026-10-21 lesson about generated-counter gates warns about. A merged tree is verified by a full suite run
on the merged head, not by a stage that stopped early. Worse, `validate.sh:102` runs
`cargo test --all-targets --all-features` **without** `--no-fail-fast`, so on this tree one failing target
suppressed every later target *and* every later text gate — the honest measurement needs the flag added by
hand, and "validate.sh is green" means something weaker than it sounds.

### Lock minimality, second pass: re-resolving does not undo the churn

The lesson recorded after #926 said "re-resolve from `main`'s lock, not hand-edit". That cure does not work
here: `git show origin/main:Cargo.lock` followed by `cargo metadata --offline` re-added the same 21
version-reference flips (`windows-sys 0.59.0 → 0.61.2` in seven parents, `socket2 0.5.10 → 0.6.5` in two,
`getrandom 0.3.4 → 0.4.3`). The newer versions were already stanzas in `main`'s graph, so any parent whose
semver range admits both is free to move when the resolver reconsiders it — an incremental resolve is not a
minimal diff. Minimality needs a **splice**: `main`'s lock plus only the four `(name, version)` stanzas the
wave's manifest introduces (`cobs 0.3.0`, `embedded-io 0.4.0`, `embedded-io 0.6.1`, `postcard 1.1.3`) plus
the two new references in the workspace stanza. The splice is then *verified*, not trusted:
`cargo metadata --offline` leaves the file byte-identical and `cargo deny --locked check` accepts it, which
proves the resolver does not want the bump — the churn was an artifact of how the lock got touched. Result:
**35 insertions, 0 deletions** instead of 45/10, and a lockfile diff a reviewer can read as "four packages
added, nothing else moved".
