## Why #739 and #740 are no-ops

`merge_single_list` builds its borrowed vector from a **slice** iterator with
`map` and no `filter`/`flat_map`, so `collect()` is `TrustedLen`-specialized and
already performs a single exact-capacity allocation. Replacing it with
`Vec::with_capacity(results.len())` + `push` cannot change anything.

Measured with a wrapping `GlobalAlloc` on exactly this code path (both branches,
borrowed stage + owned `to_string()` stage):

```
n=100  distinct scores   map(..).collect()   allocs=102   bytes=6090
                         with_capacity+push  allocs=102   bytes=6090
n=1000 distinct scores   map(..).collect()   allocs=1002  bytes=61890
                         with_capacity+push  allocs=1002  bytes=61890
n=100  equal scores      map(..).collect()   allocs=102   bytes=6090
                         with_capacity+push  allocs=102   bytes=6090
```

Byte-identical in every case. The 100/1000 allocations come from the per-item
`id.to_string()` in the second stage, which neither PR touches — that copy is
the only meaningful allocation in this function.

#740 additionally claims "up to 13.67 % latency reduction (N100_K5), verified by
benchmark" with no criterion output attached. A diff that does not change the
allocation profile or the pass count cannot produce that number; the class has
been measured four times already (#529 → #605 → #689 → #706 → #737), most
recently in `progress/LEARNINGS.md`, "Avoids reallocations is a claim about
specialization, not about the diff".

## What a real fix would look like

Return borrowed ids (`&str` tied to the input lifetime), intern them
(`Arc<str>`), or select in place instead of materialising twice. Any of those
needs a criterion run on `benches/hybrid_benchmark.rs` plus allocator counts,
per the repo's perf-claim rule.
