## #767 — clamp `chaos_strength` (verdict: merge after doc restoration)

**The fix is real and worth having.** `with_chaos_strength` took any `f32`
verbatim, so `NaN`, `±∞` and out-of-range values reached the reservoir
constructor. The change clamps finite input to `[0, 1]` and maps non-finite to
`0.0`, with unit tests for both boundaries, `NaN`, and `±∞`.

Baseline verification: the 20 builder tests on `main` are green
(`builder_advanced` 9, `builder_config_coverage` 5, `builder_config` 6), so
this is a deliberate, observable contract change rather than a silent break.

**The rubric violation — doc-comment stripping.** The second commit removes
**21 doc-comment lines** across ~7 builder methods. I checked the ADR-0094
knowledge specifically, because that is the rationale's home: **3 mentions
before, 3 after** — the ADR references survive, rewritten tersely rather than
deleted, so this is *not* knowledge loss and I am not calling it that. What
*is* removed is the feature-gate contract prose on `#[cfg(feature =
"persistence")]` methods:

- "Only available when the `persistence` feature is enabled."
- "When the `persistence` feature is disabled, this method is a no-op since
  persistence is already unavailable."

That is exactly the note class the rubric protects. A caller reading
`without_persistence` on a no-persistence build can no longer learn from the
docs that it is a legitimate no-op rather than a silent drop. **Restore these
lines in the same PR** — do not extract a child module, the file is not near
the 500 LOC gate.

**Two smaller points.**

1. `pub const fn with_chaos_strength` → `pub fn`. `clamp` and `is_finite` are
   not `const`-callable, so this is forced, but it is a **public API change on
   a root-crate builder** and deserves a line in the body so downstream `const`
   users are not surprised. All in-repo callers are runtime, so nothing here
   breaks.
2. `tests/builder_advanced.rs:184` asserted negative strength *fails*; the PR
   flips it to assert clamping. The new behaviour is defensible (clamp is
   friendlier than reject, and matches the other builder setters), but say so
   in the body — a flipped test expectation is a contract change, not a test fix.

Merge when the doc lines are back.

## #768 — complex quadratic map (verdict: close as submitted)

**Close.** This PR ships its own research scaffolding into the repository root.

Ten tracked files at the repo root are agent scratch, not product code:

They are arXiv/Crossref search helpers and ad-hoc test runners, committed at
the repository root where nothing else lives. The real work — 5 files under
`crates/csm-chaos/` — is fine in shape, but it is buried under 10 files that
must never be merged.

**The research basis is self-declared as unverified.** The body says:

> `[FALLBACK — outside this run window]` … No eligible papers were found in the
> verified research window (2026-09-18, 2026-09-25].

So the cited 2023 paper is marked fallback by the author. A chaos map added
under an `experimental-*` feature with an unverified reference and a brand-new
public API is a decision that needs a human, not a fallback fetch.

**The headline number contradicts its own table.** The body claims "~9x faster
than SLHM2D (~64.66 ns → ~7.12 ns)" while the same table records entropy,
distribution and recall as **"Not measured"**. An unattributed 7.12 ns for a
new chaos map with no published baseline and no distribution check is not a
result; it is a microbench of one path. Per the roast rubric, perf claims
without Criterion output are not review-ready, and this one is weaker than that
— there is no criterion artifact at all, only a number in prose.

**Recommendations for a resubmission:**

1. Strip all 10 scratch files. The `crates/csm-chaos/` diff is the PR.
2. Verify the paper properly and cite it without a `[FALLBACK]` marker, or
   state plainly that the design is unattributed.
3. Add the `complex_quadratic_test.rs` coverage you already have plus a
   distribution/entropy check — a chaotic map whose output is uniform in
   *appearance* is worthless; the existing chaos crates have the precedent.
4. Drop the "9x faster" claim or back it with Criterion output and a baseline
   that is on the same runner.

## #769 — `get_unchecked` in the LSH projection loop (verdict: request evidence)

**The safety argument is correct — I verified it rather than assuming.**

- `bit_pos` is produced by `rng.random_range(0..HVec10240::DIMENSION)`, so
  `bit_pos < 10240` and `byte_idx = bit_pos >> 3 < 1280`.
- The unsafe path is gated on `bytes.len() >= 1280`.
- Therefore `*bytes.get_unchecked(byte_idx)` is in bounds. The SAFETY comment
  states exactly this.

The safe path is correctly retained for the short-slice case, and the
`if let Some(byte) = bytes.get(byte_idx)` behaviour (out-of-range bit positions
simply contribute 0) is preserved for it. This is a materially better PR than
the #737/#739/#740/#754 class, which were wrong or provably zero-delta.

**Three things block it.**

1. **No evidence — and the new gate says so.** Running the merged checker
   against the live body: `exit 1`, `missing '## Performance Evidence'
   section`. This PR is exactly what the gate was built for. Note the cost
   structure: this is one branch per table, not per element, and the loop is
   `hash_bits` (≤ 64) probes per table. The claim is plausible; it is
   unmeasured.
2. **The bound is convention, not type-enforced.** `LshIndex<H: Hypervector>`
   is generic, but the SAFETY comment hardcodes `HVec10240::DIMENSION`. Today
   both impls (`HVec10240`, `BHVec10240`) have `DIMENSION = 10240`, so it is
   correct *now*. But `Hypervector::DIMENSION` is a trait constant
   (`hyperdim_ops.rs:17`), so a future impl with a different dimension would
   turn this into an **out-of-bounds read**, not a perf regression. Either
   bound the guard with `H::DIMENSION` instead of the literal 1280, or
   document the invariant on the trait.
3. **`unsafe` + `hash_bits.min(64)`** — worth stating in the body that
   `hash_bits` is capped at 64 upstream precisely so `1u64 << i` cannot
   overflow, since that is the other shift in the loop.

**To land it:** a `## Performance Evidence` section naming a
`plans/evidence/bench/canonical.json` benchmark id (or nearest comparator + new
output), Criterion output or a flamegraph, and a numeric before/after pair
measured on `csm-ref-01`. Plus recommendation 2 above, which is cheap and
prevents a future memory-safety regression.
