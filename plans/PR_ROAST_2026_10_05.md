## #834 `feat(cli): cover SIGTERM in server and watch shutdown` (Jules, draft, CI green on `09973d8`)

**Verdict: a genuine duplicate of #836 with one better coverage dimension and six
weaker ones. Not merge-worthy over #836; its one better dimension was folded into #836
at `c62f2ce` rather than re-implemented.**

It is the same design: `src/cli/shutdown.rs` selects over `ctrl_c` plus a
`SignalKind::terminate()` listener, parks the arm when installation fails, `watch.rs`
swaps `tokio::signal::ctrl_c()` for it, `mcp/server.rs` deletes `ctrl_c_shutdown` and
passes it to `with_graceful_shutdown` (`+7/-30`). Reading the two implementations side
by side, they converge — which is the strongest evidence the fix is the obvious one.

1. **Coverage credit (the reason this PR is not simply deleted from consideration):**
   its tests drive `csm mcp serve --transport sse`, the transport #821 was actually
   filed about; #836 covered `watch` only. Mine did not have that. It does now.
2. **`child.wait()` with no deadline** in both tests. If the cooperative stop regresses,
   the child never exits and the test **hangs the CI job** instead of failing it — the
   exact difference between a red build with a message and a 6-hour `in_progress`. #836
   bounds it (`EXIT_DEADLINE`, `try_wait` poll, kill-and-panic).
3. **Readiness is a guessed sleep** — `sleep(200ms)` / `sleep(300ms)` under the comment
   "Give process a moment to initialize signal handlers", with nothing verifying the
   child reached its serving state. Two failure modes, both silent: too short and the
   signal lands before the handler installs (exit 143, red for the wrong reason); too
   long and slow CI is just flaky. #836 waits for the line each command prints *at that
   moment* (`Press Ctrl+C to stop.` / `MCP SSE server listening on`) and settles after.
4. **No `--database`, so the tests write into the repository.** `csm watch` and
   `csm mcp serve` are spawned bare; with no `--database`, `src/cli/args.rs:20` falls
   back to git-local storage, i.e. `.git/memory-index/csm.db` inside the CI checkout.
   A test that mutates the checkout it is running in is not hermetic. #836 passes an
   explicit `tempfile` path to every spawn.
5. **`shutdown_signal_compiles` is a vacuous test.** Its body is `let _fut =
   shutdown_signal();` — an `async fn` call constructs a future and does *nothing*; it
   is not polled, so it asserts only that the file compiles, which the build already
   asserts. It raises the test count by 1 with zero kill potential, and the *same file*
   is then excluded from mutation testing by this PR's own `--exclude
   "src/cli/shutdown.rs"`. A no-op test plus an exclusion is the opposite of evidence.
6. **`sig.recv().await;` discards the `Option`.** A SIGTERM stream that closes without
   delivering a signal (`None`) falls through to `info!("Received SIGTERM; stopping")`
   and resolves the shutdown — a non-event becomes a request to stop a server. #836
   treats `None` as "not a shutdown request" and parks, consistent with its
   installation-failure arm.
7. **`--exclude-re "replace shutdown_signal"` works — and that is what makes the pair of
   exclusions damning.** My first read of this line was *"a description string can never
   match a name regex, so it is inert"*, and it was **wrong**: I read a `tail`-truncated
   `--list` output as a result. Measured properly with counts against this branch's
   analogous free function (`src/shutdown.rs`, baseline 3 mutants —
   `operator_shutdown`, `sigint`, `sigterm`):

   | `--exclude-re` | listed | reading |
   |---|---|---|
   | `"replace operator_shutdown"` | 2 | the pattern set matches the mutant **description**, so `replace <fn>` is a valid form |
   | `"operator_shutdown"` / `"sigterm"` / `"replace sigint"` | 2 | ditto |
   | `"shutdown::"` | 3 | names are **not** module-path-qualified |
   | `"zzz_no_match"` | 3 | control: a non-matching pattern changes nothing |

   Cross-check on the repo's own pre-existing entry, since "dead exclusion" was my hypothesis:
   `src/mcp/handler.rs` baselines at 12 mutants and `--exclude-re "McpHandler::"` leaves 8,
   so that line does real work (impl-qualified descriptions like
   `McpHandler::read_resource`).

   The real finding is therefore not a dead flag but a **coverage hole converted into a
   policy line**: `--exclude-re "replace shutdown_signal"` is redundant with the
   `--exclude "src/cli/shutdown.rs"` added directly under it (a file glob already removes
   every mutant in the file), and the module needs excluding only because its behavioural
   tests sit in `tests/cli_integration.rs` — a `tests/` target the mutation fast profile
   never runs (`scripts/mutation_test.sh:142` passes `--lib -p csm-retrieval -p
   chaotic_semantic_memory`). `replace shutdown_signal with ()` would be unkillable there:
   the in-profile unit test is `let _fut = shutdown_signal();`, which passes unchanged
   under the mutant because constructing a future polls nothing. So the mutant is real,
   nobody can kill it in the profile that runs, and the PR's response is to exclude the
   file rather than to place a kill-capable test where the gate can see it — the exact
   #817 failure mode this repo already documents.
8. **Public API growth with no consumer.** `pub mod shutdown` + `pub use
   shutdown::shutdown_signal` + a `pub fn` line, which is why `llms.txt` is `+6`.
   Nothing outside the crate can use a process-signal park meaningfully, and the module
   is also *ungated* — `signal` is a target-gated tokio feature (`Cargo.toml:197-202`,
   non-wasm only) and `pre-release-gate.yml` has no caller, so no CI job checks the root
   crate for `wasm32` with `cli` on. #836 keeps the primitive `pub(crate)` behind
   `#[cfg(all(not(target_arch = "wasm32"), feature = "cli"))]`, so `llms.txt` is
   untouched and the wasm question does not arise.

## #835 `perf(retrieval): defer score normalization scaling in merge_single_list` (Jules, draft, `commitlint: FAILURE`, mergeState `BLOCKED`)

**Verdict: an unevidenced resubmission of the closed #763, currently unmergeable. CI is
not green — `commitlint` COMPLETED/FAILURE — so "green on a stale head" cannot even be
the defence.**

1. **Same idea, same file, same function as #763** (closed): `crates/csm-retrieval/src/
   hybrid.rs`, `merge_single_list`, defer the min-max scale past top-k selection. The
   titles differ by a word — "defer score scaling in single list hybrid merge" vs
   "defer score normalization scaling in merge_single_list".
2. **It drops the benchmark entirely.** #763 was roasted for citing a bench that never
   reaches the changed path; removing the bench removes that critique and removes the
   claim's support with it. The body's "2·N → 2·k floating-point operations" is
   arithmetic, not measurement, and there is no `## Performance Evidence` section —
   which is precisely the section `scripts/check-perf-pr-evidence.py` reads on a
   `perf(...)` title.
3. **Title churn instead of history**: 4 commits, three headed
   `perf(retrieval): defer score normalization scaling in merge_single_list` and a
   fourth re-typed `refactor(retrieval): …` — still failing commitlint. Changing a
   commit type to get past a gate, repeatedly, is gate-dodging; the failure is in
   something else the linter checks and it was never looked at.
4. **It inherits a named defect from the review it is resubmitting past.** The
   `pr-roast-triage` rubric already records, from the #763/#790/#793 family: *"when
   `k == N` the partition is skipped, so deferring per-element work is a pure
   regression — guard it"*, and *"a FLOP-count reduction inside a function dominated by
   allocation/partitioning is **not** a speedup"*. #835 is that exact deferral with
   neither the guard nor the measurement, so the skill's own text refutes it. Citing the
   rule beats re-litigating the arithmetic.
5. **Correctness is *not* the objection and should not be quoted as one.** Min-max
   scaling is monotone non-decreasing when the factor is ≥ 0, so selecting on raw
   scores and scaling the survivors is equivalent **provided `min`/`max` are still
   computed over the full list before selection**. That one precondition is the only
   thing that would make this a silent ranking bug, and nobody has read the diff for it
   — including me, at this writing. If this is ever revived, that line is the review
   (and the rubric's "test the public input domain, not just internal callers" applies:
   a negative factor reverses ordering, so raw-score selection would be wrong).

## #836 self-roast (`fix(mcp): stop both long-running servers on SIGTERM, not only SIGINT`)

- **What this PR lacked at `03a9032` and a competing draft supplied:** the SSE server
  had no process-level signal test. Fixed at `c62f2ce` by adding
  `serve_sse_stops_cooperatively_on_sigterm`/`_sigint`, which is why the branch now
  strictly dominates #834 on coverage.
- **The new SSE tests pin the exit path, not the shutdown hop.** No MCP request is
  issued, so the handler's framework is never initialized and `handler.shutdown()` has
  no reaper to stop — exit 0 proves the transport resolved, not that the ADR-0099 hop
  did useful work. Stated in the test's own doc comment rather than implied by a green
  check.
- **Red was demonstrated, not argued.** Deleting the SIGTERM arm from
  `operator_shutdown()` turns exactly the two SIGTERM tests red with
  `unix_wait_status(15)` while both SIGINT tests stay green; the file was then restored
  and `git diff HEAD -- src/shutdown.rs` re-checked empty before re-running.
- **Neuter-resistance check for the folded-in coverage:** an `if false` around the
  shutdown hop still exits 0, which is why the assertion is the OS-level exit status and
  why `src/mcp/server_tests.rs` continues to assert the hop in-process.
