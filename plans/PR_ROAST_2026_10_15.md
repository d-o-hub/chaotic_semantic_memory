## #893 `perf(hyperdim_binary)`: eliminate zero-init + zero-shift fast path — closed, no impact

Claim: `MaybeUninit` in `from_bytes` / `from_hvec` / `to_hvec` removes "1 280
bytes of memory writes per conversion", plus a `permute` zero-shift fast path.
Diff: `crates/csm-core-lib/src/hyperdim.rs`, `.../hyperdim_binary.rs`,
`Cargo.lock` (3 files, +71/−68).

**1. Both halves are re-filings of ideas this repo already measured and closed.**

- `permute` zero-shift: #800 (kept open on evidence, then closed —
  `plans/PR_ROAST_2026_10_02.md`: direct call **81.7 → 57.3 ns** 6/6 rounds,
  product path `text_encoder/encode_short` **2 684 → 2 734 ns** = noise),
  #814 (`2026_10_03`), #819 (`2026_10_04`, closed NO-IMPACT), #875 and #879
  (`2026_10_12`, both closed).
- `MaybeUninit` conversions: #783 (`2026_09_28`, disassembly — old/new folded
  to the same address, no `memset` in the old body), #863 (`2026_10_09`),
  #875 (`2026_10_12`).

`grep -rn 'permute' plans/PR_ROAST_*.md` finds five prior verdicts on these
lines; new task id, new branch name, same 5-line hunk.

**2. The premise is refuted on the toolchain this workspace pins.** Bodies
transcribed verbatim from `origin/main` and the PR head, identical signatures,
`rustc 1.88.0 -O -C codegen-units=1`, `#[no_mangle] #[inline(never)]`, linked
into one binary:

```
nm -C --defined-only dse            # from_bytes, little-endian arm
0000000000014b50 T from_bytes_main  # memcpy only, no memset, LLVM already
0000000000014b50 T from_bytes_pr    # dead-store-eliminated the zero-fill
```

Same address ⇒ byte-identical code ⇒ there is no zero-fill left to remove in
the conversions. For the aligned `permute` path the PR's own placement is not
sufficient either:

```
0000000000014f20 T perm_main      # memset + memcpy  (init before the branch)
0000000000014fd0 T perm_pr        # memset + memcpy  (init inside the branch,
                                  #  after `word_shift == 0 { return *self }`)
0000000000014cd0 T perm_general   # memset           (bit_shift != 0, untouched)
```

Moving the initializer into the branch **does not remove the `memset`** when
`word_shift != 0` — LLVM cannot prove that
`result[..80-w]` + `result[80-w..]` covers all 80 words for a runtime `w`. The
only path where the `memset` disappears is `word_shift == 0`, which the PR
short-circuits with `return *self` — i.e. exactly #800's measured change.

**3. Also present, and disqualifying on their own terms:** `Cargo.lock` carries
seven `windows-sys 0.52.0 → 0.59.0` edges, `rustls 0.23.45 → 0.23.46` and a
`getrandom 0.4.3 → 0.3.4` **downgrade** — resolver churn unrelated to the diff.

**4. CI truth (annotations):** `commitlint` red — `perf PR evidence gate:
missing '## Performance Evidence' section in the PR body`; Codacy red —
`Detected 'unsafe' usage, please audit for secure usage`.

**Correctness is not in question**: the `assume_init`s follow full-width 1 280-byte
writes and `permute(0)`'s identity is already asserted by
`crates/csm-core-lib/src/hyperdim_tests.rs:48` (`assert_eq!(v, v.permute(0))`).
Verdict: closed **as submitted, no demonstrated impact** — not as incorrect.

## #889 `perf(encoder)`: single-token fast path + capacity pre-allocation — keep open, three repairs

Diff: `crates/csm-core-lib/src/encoder.rs` (+1 test), `benches/embedding_benchmark.rs`
(`bench_encode_single` → `encode("hello")`, which *does* enter the new fast
path — unlike #800's `permute(321)`, the bench is parameterized correctly).

**Measured (out-of-tree A/B worktrees, same host, 200 000 iters/arm, 6 rounds —
`main` then head — on `csm-core-lib` release, probe removed afterwards):**

| round | `main` encode("hello") | head encode("hello") |
|-------|----------------------|----------------------|
| 1 | 590.6 ns | 468.3 ns |
| 2 | 577.3 ns | 459.6 ns |
| 3 | 581.0 ns | 457.5 ns |
| 4 | 572.2 ns | 494.0 ns |

6/6 rounds same sign ⇒ **≈ −20 % single-token encode latency**. Allocation
profile: `2 allocs / 1 344 B` → `1 alloc / 64 B` (the surviving 64 B is the
token `Vec<&str>`); the `to_bytes()` digest over all 80 `u128` words is
identical on both revisions for `"hello"` and `"alpha beta gamma"` ⇒
behaviour-preserving, and by construction: `bundle(&[v])` returns `v`
(`hyperdim.rs:118`) and `permute(0)` is the identity
(`hyperdim_tests.rs:48`), so the fast path is exactly the slow path for
`tokens.len() == 1 && ngram_size.is_none()`.

**Repairs required before merge (the PR is not review-ready as submitted):**

1. **Drop the `with_capacity(tokens.len())` + `push` hunk** — provably
   zero-delta. Three-token encode measures `2 allocs / 3 904 B` on **both**
   revisions: `tokens.iter().enumerate().map(..).collect()` is
   `ExactSizeIterator`-specialized. This is the #754/#776 finding again
   (LEARNINGS 2026-09-25).
2. **Replace the body's numbers; they are false.** The body claims
   "~4.51 µs → ~675 ns (~85 %)". Measured: **590.6 → 468.3 ns**. The claimed
   "after" (675 ns) is *slower* than the head measures (468 ns) and the claimed
   "before" (4.51 µs) is 7.6× the measured `main` baseline; 4.51 µs is #776's
   own claimed **post-change** number for 3-token input (#776, closed
   2026-09-27 for exactly this: behaviour-preserving half, no artifact).
   The gate's `## Performance Evidence` section must carry the measured pair
   (`encode_single_1tok`, plus `text_encoder/encode_short` unchanged ≈ 3.0 µs).
3. **The new test cannot distinguish the paths.** `encode_single_token_fast_path`
   compares `encode("hello")` to `token_to_hvec("hello")`, which the *slow* path
   also satisfies (bundle-of-one). Verified by applying the mutant
   `tokens.len() == 1` → `!= 1` in a worktree: `cargo test -p csm-core-lib --lib
   encoder` → **10 passed**. A three-token assertion
   (`encode("alpha beta gamma") != token_to_hvec("alpha")`) kills it.

CI: `commitlint` red — the same perf-gate annotation as #893; `Cargo Deny` red
is the known external flake (`Unable to authenticate to FlakeHub`), not the
diff. Context for repair 3: `scripts/mutation_test.sh:146` scores
`--lib -p csm-retrieval -p chaotic_semantic_memory`, so `csm-core-lib` is
outside the mutation gate today (pre-existing TODO in that script).

## #887 dependabot: uuid 1.26.1 → 1.28.0 in `/fuzz` — closed, not mergeable under the MSRV

CI truth (job `115434949624`, run `38437397912`): `Fuzz Workspace Build` exit
101 —

```
uuid@1.28.0 requires rustc 1.89.0
Either upgrade rustc or select compatible dependency versions with
`cargo update <name>@<current-ver> --precise <compatible-ver>`
```

Measured against the published crates: `uuid` `1.26.1` → `rust_version 1.85.0`
(what `main`'s `/fuzz` **and** root lock hold), `1.27.0` → `1.89.0`, `1.28.0` →
`1.89.0`. The workspace pins `rust-toolchain.toml` `channel = "1.88.0"` and
`rust-version = 1.88`, so **no compatible upgrade above 1.26.1 exists**; the
"precise downgrade" the log suggests lands back on the version already in the
lock. The bump is also transitive in the fuzz workspace (`uuid` is a dependency
of `csm-persistence`/`libsql`/`libsql_replication` there), so the same break
would reproduce in the root lock if the root entry were bumped.

Recurrence cure (owner decision, both options cost something): either add a
`uuid` ignore with a "remove when the workspace MSRV moves to 1.89" reason to
the two `cargo` entries of `.github/dependabot.yml` (precedent:
`libsql-sqlite3-parser`), or move the MSRV to 1.89 — a whole-workspace decision,
since `rust-toolchain.toml` is consumed by every CI job. Closing the PR does not
prevent dependabot from re-filing it next week.
