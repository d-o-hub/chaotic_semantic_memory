## Why not "merge the useful one"

#956 is the only PR with a real defect behind it, and its *mechanism* is this repo's own blessed pattern
(`pub const` + `.min()` at the boundary — `MAX_TOP_K_LIMIT` at `csm-retrieval/src/bm25.rs:15,241`, #684;
the #899/#900 record at `PR_ROAST_2026_10_16.md:38-50`). It still cannot merge, for two reasons that are
independent of the commitlint failure:

1. `input_dim` is a **shape invariant**, not a size hint. `chaotic_lsh.rs:44-46` and `:88-90`, and
   `voronoi_lsh.rs:46-47` and `:78`, return an all-zero `[u64; 160]` when `input.len() != self.input_dim`.
   A silent clamp therefore converts the DoS it targets into *every query hashing to the zero code* —
   invisible to the caller, because `input_dim` is private and no accessor is added. In an
   associative-memory crate that is a data-integrity failure dressed as a fix.
2. The number does not do the job. At `MAX_INPUT_DIM = 16_384` the allocation is **640 MiB** per
   `ChaoticLsh` (`10240 × 16384 × 4`) and **1.25 GiB** per `VoronoiLsh` (`10240 × 2 × 16384 × 4`), while
   the largest dimension any in-repo caller uses is **1536** (`benches/chaotic_hashing_voronoi.rs:8`) and
   the rest are ≤ 128. It permits GiB-scale allocations and fires only in the case it corrupts.

Rule 10 then decides the mechanism: close, and re-create from current `main` — not rebase, not retitle
through a bot head. Filed as **#961** with the five requirements the re-created PR must carry.

## main went red on the #947 squash subject (14:13Z, found while waiting for #962)

**Symptom.** Main CI run **41059071360** (event `push`, head `3953e818f40783d4ac8ebb9228ce2cc48c47ef8c`)
failed one job: `commitlint`, check-run id **124073904392**. Its annotation was the useless
“Process completed with exit code 1”, so the truth came from `gh run view 41059071360 --log-failed`
(1027 lines, every one prefixed `UNKNOWN STEP`): the step ran
`npx commitlint --from ae117fb987c6412e5c8f99d0712665594129a3a8 --to 3953e818f40783d4ac8ebb9228ce2cc48c47ef8c --verbose`
and printed `✖ header must not be longer than 100 characters, current length is 104 [header-max-length]`.

**Cause, measured.** The offending subject is the #947 squash-merge commit itself:
`feat(core): audit wave — durable-first mutations, versioned export, Streamable HTTP, bounded OTLP (#947)`
— **104** chars. The PR *title* was 97, and GitHub appends ` (#947)` (7 chars) to the squash subject. So
the title was within `header-max-length` and the merged message was not.

**Why no gate saw it.** On the PR, commitlint lints the **branch commits**
(`--from origin/main --to HEAD`); after a squash-merge, `main` receives a **different string** — the PR
title plus ` (#NNN)`. No pre-merge check measures the message main actually gets. It surfaced on main
only because the push range started at the *previous* main commit, dragging the bad subject into the
linted set.

**Consequence and recovery.** Not a code defect and not something to “fix” with a commit: main
self-heals on the **next merge**, because the range becomes `--from 3953e818… --to <new squash>` and the
bad subject leaves the set. The one thing that would make it sticky is another over-length squash, so
the budget for every open PR is `100 − len(" (#NNN)")`. Measured for the two in flight: **#962**
title 73 → subject 80, **#963** title 85 → subject 92. Both safe. The jobless `release.yml` run
**41070030431** (workflow_run on `3953e818`, created 14:13:59Z, success, 0 jobs) is a *consequence* of
the red CI it followed, not new evidence about the workflow being unparsable — do not cite it as such.
