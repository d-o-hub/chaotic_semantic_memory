## `main` at `123e5e89` — verdict: **RED on one job, and the cause is an unpack, not a compile**

`Test DuckDB Companion` (job 127295486169, attempt 1, never re-run) is the only failing job on push run
42041881050: 26 succeeded, 3 skipped (`miri` on a no-Rust diff, `mutation-test` and `mutation-shard` are
PR-only). `--log-failed` says:

```
error: failed to run custom build command for `libduckdb-sys v1.20000.1`
thread 'main' panicked at .../libduckdb-sys-1.20000.1/build_bundled_cc.rs:65:10:
unpacking bundled DuckDB sources: Os { code: 39, kind: DirectoryNotEmpty, message: "Directory not empty" }
```

- **Not a native-compile failure.** The panic is at the *extraction* of the bundled DuckDB tarball, before any
  C++ translation unit: the step opened at 14:51:05 and died at 14:52:14, 69 s later, while this repo's own
  comment (`ci.yml:446-456`) measures a cold C++ build at ~20 min. Exit status 101 is a Rust panic — a `cc`
  failure surfaces as `error: could not compile`, not as a build-script panic — and errno 39 (`ENOTEMPTY`) means
  the destination already had content, i.e. carried-over build state rather than a broken toolchain.
- **The cache is where that state comes from, and it is currently absent.** `shared-key: test` is shared by six
  `ci.yml` jobs (`:361`, `:421`, `:467`, `:598`, `:812`, `:899`), so whichever of them saves last writes the
  residue. Measured now, `refs/heads/main` holds exactly one entry — `v0-rust-cli-Linux-x64-e9cbe196-f3047159`
  (306 MB) — and **no** `v0-rust-test-*`, so a re-run restores nothing for that key and builds cold. A plain
  re-run is therefore a real test, not a coin flip. If it fails at the same line anyway, the carrier is not the
  branch cache and the honest fix is `cargo clean -p libduckdb-sys` before the step, not another retry.
- Infra-class per `AGENTS.md` Phase 1 step 4: re-run the attempt before writing any fix. **The re-run has not
  been issued** — it is shared state and is waiting on an explicit go-ahead.

- **A capability claim sat in the docs for six months, false.** ADR-0039 lists "Trusted Publishing for crates.io
  (OIDC-based, no tokens)" as delivered and its own positive consequence says "No long-lived API tokens
  (security)"; `book/src/release.md:123` repeated it. Nothing in the gate set compares a *capability* sentence
  with the workflow that would have to implement it, so ADR parity and docs-link and version checks all passed
  over a statement that was never true. Amended in place (0039, 0042 item 1, the book) rather than quietly
  rewritten, because the record of the false claim is the useful part.
- **Worse than a missing feature: a shipped probe that could not pass, guarded by a fixture that kept it
  alive.** #967 added a step curling `/api/v1/me` with the registry credential and requiring HTTP 200.
  crates.io serves that route behind `AuthCheck::only_cookie()`, so no token — live, expired, or revoked —
  answers 200. `scripts/test-verify-release-step.sh` stubbed exactly that 200, which is the only reason the
  dead code survived review: a fixture that supplies the assertion's own expected value tests the wiring, not
  the behavior. Deleted, and the replacement assertions are structural (`secrets.CARGO_REGISTRY_TOKEN` occurs
  zero times; the auth step precedes every token consumer; forbidden triggers absent from `on:`) plus
  behavioral replays (unset token → exit 1 and zero `cargo publish`; 2-of-9 live → exit 1 naming the seven).
- **I designed this wrong twice before writing it.** First as a job inside `release.yml` — impossible,
  `handle_github_token_inner` refuses OIDC assertions minted from `workflow_run`, and that is what triggers
  `release.yml:4-7`. Then as a tag-triggered workflow — also impossible, `release.yml:250` pushes the tag with
  `secrets.GITHUB_TOKEN` and a `GITHUB_TOKEN` push spawns no run. Both dead ends came from planning against the
  RFC's happy path instead of the server's code. `workflow_dispatch` is not the elegant answer, it is the only
  one of the three that can work.
- **Accepted consequence, stated out loud:** `release.yml` can no longer turn green by itself. `verify-release`

  operator which workflow to dispatch. That makes publishing a human step in the release *signal*, which is the
  point — but it does mean every release needs a second action, and the docs say so
  (`agents-docs/release-safety.md` step 7, `book/src/release.md`) instead of leaving the next reader to
  discover a red job.
- **Atomicity:** one workflow added, one job deleted, the two `needs:` lists that named it, its fixture moved
