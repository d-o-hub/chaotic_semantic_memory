## #1018 — closed: no demonstrated impact

- **The mechanism is refuted at this exact site.** `from_bytes_old` and `from_bytes_new` share
  address `0x179c0`. LLVM already dead-store-eliminates `[0u64; 160]` because
  `copy_nonoverlapping(…, 1280)` overwrites all of it; there is no 1 280-byte zero-fill left to
  remove. This is the same function and the same premise already closed at #783, #893, #875 —
  the measured disassembly in `plans/.archive/2026-11-03-historical/PR_ROAST_2026_10_15.md:49-50`
  puts both variants at `0x14b50` on this same toolchain.
- **37.8 % cannot come from byte-identical code.** The interleaved run sign-flips; the claimed
  74.13 → 46.07 ns is a one-shot reading of noise.
- **The cited baseline does not contain the changed benchmark.**
  `plans/evidence/bench/canonical.json` has `hvec_from_bytes` (median **51.60 ns**) and no
  `bhvec_from_bytes` row at all. The PR changes `BHVec10240::from_bytes` but cites
  `hvec_from_bytes` as its baseline, and its 74.13 ns "before" matches neither that row nor its
  own 46.07 ns "after".
- Correct but zero-delta: the `MaybeUninit` + `read()` form is sound (all 1 280 bytes are written
  before the read), so the close is on impact, not correctness. No unit test accompanies the
  change either.

## #1017 — closed: no demonstrated impact

- **Not folded, but only store ordering differs.** `to_bytes_new` stores `len`, stores `ptr`,
  `memcpy(0x500)`, stores `cap`; `to_bytes_old` does `memcpy(0x500)`, then stores `len`, `ptr`,
  `cap`. Both bodies contain exactly one `memcpy`, **no `memset`, and no bounds or capacity
  check** — the stated mechanism ("avoid slice bounds and capacity checking in
  `extend_from_slice`") is already absent from main's binary because the source is a
  compile-time-sized `&[u8; 1280]`.
- **The 2 % claim is inside host noise.** Interleaved legs: −23.7 %, +1.5 %, −3.4 %, +17.8 %; no
  consistent sign. A single `target/criterion/hvec_to_bytes/new/estimates.json` is an artifact,
  not a change report: no CI, no `p0.05` verdict, no before-artifact.
- **The "before" number does not reconcile with the canonical baseline.**
  `plans/evidence/bench/canonical.json` records `hvec_to_bytes` median **88.91 ns**
  (CI 87.01–91.85), not the cited 96.04 ns.
- This is #783's `to_bytes` half again: "same `alloc(1280)` + `memcpy(1280)`, differ only in
  instruction scheduling. No `memset` in either body. Its claimed ~3.7 % needs reproducible
  benchmark evidence." A one-shot 2 % does not supply it.

## #1016 — closed as submitted

1. **Research scaffolding in the repo root:** a 3 695 968-byte compiled ELF `test_sparsity`, plus
   `pr_body.txt`, `test_csm_chaos.rs` (`fn main() {}`) and `test_sparsity.rs`. The rubric rejects
   committed scaffolding; the PR body itself is a file in the diff.
2. **The sparsity mask is unreachable for every documented value.** `Slhm2d::next_value()` is
   documented and tested as uniform `[0, 1)` (`crates/csm-chaos/src/maps/hyperchaotic.rs:41-62`,
   `test_slhm2d_range`). The PR computes `prob = (v1 + 1.0) / 2.0`, which is `[0.5, 1.0)`, then
   `if prob <= sparsity`. For the documented `0.1`–`0.5` range nothing satisfies it, so the
   projection matrix is **all zeros**; the PR's own benchmark uses `sparsity = 0.1`, and three of
   its tests use `0.1`/`0.2`/`0.15`. The "~25.4 ms" headline is the cost of sorting 10 240 zeros.
   The tests mask it: `test_flyhash_sparsity` only asserts `non_zero > 0` and uses `1.0`;
   `test_flyhash_try_new_math` compares `0.9` vs `0.5`, where the second side is trivially empty.
3. **The cited paper argues against the value claim.** [arXiv:2611.05791](https://arxiv.org/abs/2611.05791)
   exists and its abstract states the quality advantage does not translate: "at equal bits
   FlyHash's codes are larger and slower to compare than SimHash's, and HNSW dominates both hash
   methods at ordinary scale". The PR reports "competitive retrieval capabilities" with recall
   "Not measured", beside a measured **2x latency regression** — the #768 self-contradicting table.
4. **Memory/API cost with no consumer.** `projection_matrix` is a dense `Vec<f32>` of
   `10240 * input_dim` — 60 MiB at 1536, 160 MiB at `MAX_INPUT_DIM` — public and
   `Clone + PartialEq`; "sparsity" only zeroes entries, it does not store sparsely. Nothing
   constructs or consumes `FlyHash`; it is dead code behind a non-default feature, no ADR, no
   retrieval integration.

Also: `try_new` silently clamps `sparsity` to `0.0` and `top_k` to `1..=10240` instead of
rejecting, contradicting its own doc (`0.0 < sparsity`) and the `try_` contract. A resubmission
needs the sampler fed as `[0,1)` (`v1`, not `(v1+1)/2`), a ratio test at 0.1/0.5/0.9, measured
recall or no quality claim, a sparse representation with a memory bound, a consumer, and no root
scaffolding.
