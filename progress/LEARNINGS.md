## Security Patterns
- **Optimization domains must match the public API (2026-09-30, #790/#793):** positive weights from one internal caller do not justify raw-score top-k selection in a public arbitrary-weight API; negative weights reverse ordering. Close incorrect duplicate submissions as submitted, while distinguishing their independent unmeasured ideas from proven no-ops. Require parity tests over supported inputs and benchmarks reaching the changed branch.
- **Path hijacking (CWE-426)**: resolve executables to absolute paths; filter PATH to exclude relative entries.
- **Public API input bounds (2026-08-07/17 cluster)**: NaN `threshold` in `prune_decayed_associations` silently deleted all associations; unguarded `n: usize` in `encode_with_ngrams` overflowed `windows(n+1)`; unbounded `ConceptBuilder::with_ttl` overflowed `now + ttl`. Prevention: finite-limit validation on all public f32/f64 rate/score/threshold params (even when helpers like `validate_association_strength` exist — non-inserting APIs skip them); named `MAX_*` constants for usize size/window params; saturating arithmetic on all time/size intervals.
- **A duplicated type makes a clamp fix half-done (2026-10-03, #806 → #816)**: two `ConceptBuilder`s existed — the owner (`crates/csm-memory/src/concept_builder.rs`) already clamped TTL, the generic copy in `singularity_types.rs` did not, and *the copy* is what `src/framework.rs`, `src/framework_ttl.rs` and `src/framework_ops.rs` imported. #806 patched the copy and the bug closed, while the reason it existed (one name, two bodies) stayed. Collapsing is the actual fix, and three things made it safe rather than heroic: (1) the generic parameter was never instantiated at a non-default `H`, proved by grepping every `ConceptBuilder<` spelling — otherwise deleting it is a real API break; (2) every public path keeps resolving, via `pub use crate::concept_builder::ConceptBuilder;` added to `singularity.rs`, so `chaotic_semantic_memory::{singularity::,prelude::}ConceptBuilder` survive and "not breaking" is verified rather than hoped; (3) two `tests/arch_fitness.rs` guards make re-duplication fail loudly — one asserts exactly one `struct ConceptBuilder` workspace-wide, the other passes all five public spellings to a function taking the owner type, so a second lookalike becomes a compile error instead of a silent behavioural split. Also audit the *behavioural* deltas a collapse applies to production: the copy derived `Clone` (no call site used it) and its `with_metadata` took `impl Into<Value>` infallibly, while the owner takes `impl Serialize` and captures the failure into `build()`'s `Result` — correct per ADR-0012, but a semantic change on every path, so it belongs in the changelog rather than under a "pure dedup" title.
- **Facade copies can be newer than the owner (2026-09-18)**: PR #700 fixed the `std::env` mutation race only in the root facade copies of the embedding tests; `crates/csm-embedding` still carried the racy pattern *and the false "single-threaded test is sound" SAFETY comment*. Deleting the facade copies first would have deleted the fix. Diff a duplicate pair in both directions before removing either side; port owner-side first.
- **"Verbatim duplicate" is a claim, not a finding (2026-09-18)**: a scout proposed six root integration files as duplicates of other root files; normalized body comparison found **zero** identical bodies, and hand review showed the pairs assert different things (metrics accounting vs result membership, error variants vs accept/reject edges, retrieval-after-TTL vs stored expiry). Use a body comparator first (`comment/whitespace-normalized`, braces matched) and read the survivors; same test name across two files is a lead only.
- **An empty feature hides a second implementation (2026-09-18)**: `csm-core-lib` declared `experimental-neural-circuit = []` while holding a full copy of the `csm-chaos` CDNCM map; the root forwarded the feature to `csm-chaos` only, so the copy was unreachable and invisible to normal builds. Grep for features that enable nothing (`= []`) and check whether their modules duplicate an owner.
- **Namespace validation (CWE-770)**: 128-byte limit, non-empty, no control chars — apply to any param that becomes a DB key.
- **DoS bounds**: Graph `MAX_DEPTH=32`, `MAX_RESULTS=10K`; batch `max_batch_size=1000`.

## Performance Patterns
- **Cache invalidation is part of retrieval correctness (2026-09-29)**: a similarity cache keyed only by query and `top_k` becomes a false-negative cache when inserts or graph mutations do not clear it. Invalidate on every mutation that changes candidates, including extension methods such as `clear_associations`, and test probe → mutate → identical probe; capacity eviction must also distinguish a new ID from an upsert before evicting.
- **Bucketed candidate recall is a function of corpus size (fixed 2026-09-21)**: `bucket_probe_width` fixes the bucket mask, so recall@10 fell as the corpus grew — 0.604 (10k) → 0.576 (50k) → **0.208** (200k) at floor 8, and **0.016** at the floor-2 default. The sweep showed the dominant cause was **index-order truncation** of an oversized bucket (widths 2–6 all returned exactly `max_candidates`), not the width per se. Fix: the configured width is a floor that scales with N, candidates within one masked bit are accepted, and a probe beyond 2× the budget declines so the caller scans exactly. Same class: HNSW at fixed `ef_search` drifts 0.908 → 0.800 over the same range.
- **Measure the site the workload hits, not the site the hypothesis names (2026-09-27, #781)**: the queued clone-hunt target from the #754 roast (`score_specific_candidates`, 257 allocs at n=256) is ~25 of the 2 209 allocations a default bridge query performs; the dominant sink was `ConceptGraph::match_tokens`/`expand` materialising every matched id and expanded label before the caller truncates to `top_k`. Borrowing the path (`match_tokens_ref`/`expand_ref`, positions-based scoring, `&str` merge keys) took 2 209 → 151 allocs/query and 881 → 577 µs on the wide-fan-out bench. Adjudicate by tracing bench → function → workload; keep owned wrappers so published signatures survive.
- **Paired A/B on a noisy box: trust the direction, discard polluted legs (2026-09-27, #781)**: the same expansion bench measured 826–918 µs, 555–621 µs, 733–826 µs and 870 µs–1.58 ms across four windows while the cached comparator drifted 9.1–13.4 µs (±30%): adjacent paired comparisons agreed (new faster by 25–45%), and the leg whose first sample sat outside every other window was discarded. Report the paired change with its CI, name the comparator drift, and never quote a lone absolute.
- **ILP over SIMD**: 4 independent accumulators in hot loops often beat SIMD (avoids STLF stalls).
- **Branchless bitmasks**: `w |= (cond as u128) << j` minimizes branch misprediction.
- **Zero-alloc interning**: `Arc<str>` + `get_mut`/`get_key_value` double-lookup for BM25 terms; `HashSet<&str>` + single-pass `insert()` kills the contains+insert double lookup (PR #679).
- **Rayon gating**: parallelize only when N >= 32; scheduling overhead dominates small ops.
- **Bitmask modulo**: power-of-2 buckets → `& (N-1)` instead of `% N`.
- **f32::min/max vs operators**: `.min()`/`.max()` compile to `llvm.minnum`/`llvm.maxnum` — MORE vectorizable than if/else. Do NOT "simplify" to `<`/`>` (reverses mutation-test design, strips docs, adds exclusion debt).
- **A perf gate that asserts arithmetic is worse than no gate (2026-09-17)**: `projected_10m_concepts_memory_stays_under_12mb` multiplied a configured bytes/concept constant and passed for months while the shipped representation needed ~1 000x more memory (measured: 4 691 B RSS / 2 850 B persisted per concept, 43.7 GB / 26.5 GB at 10 M). The constant described an unimplemented design (ADR-0024 phase-2 product quantization). If a claim cannot be measured in CI, mark it unverified rather than encoding its arithmetic as a test — and when the measurement lands, publish the manifest next to the number.
- **Conversion elimination beats kernel tuning**: BHVec10240::hamming's ~2.6–2.75× came from removing two 1,280-byte `to_hvec()` copies, not new SIMD. Measure the full call path, not just the kernel.
- **Separate zero-fill elimination from scheduling effects (2026-09-28, PR #783)**: in the inspected x86_64/rustc 1.98.1 builds, LLVM dead-store-eliminates the `[0u64; N]` initializer overwritten by a full-width `memcpy`: an old-only build disassembles to a bare `memcpy`, and old/new `from_hvec`/`from_bytes` variants fold to the **same address** (byte-identical code). `to_bytes` keeps the same alloc+memcpy but changes instruction scheduling, so there is no demonstrated zero-fill-elimination benefit, not a blanket zero-codegen-delta finding. Disassembly cannot dismiss every timing delta as noise; any scheduling-speedup claim needs reproducible affected-path benchmarks. Inspect the mechanism first; raw `rustc --emit obj/asm` (rustc 1.98.1) drops unreferenced `pub fn`s, so compile variants `#[no_mangle] #[inline(never)]` into a linked binary instead.
- **"Avoids reallocations" is a claim about specialization, not about the diff (2026-09-15)**: `.iter().map(..).collect::<Vec<_>>()` over a slice is `TrustedLen`/`ExactSizeIterator`-specialized, so `Vec::from_iter` already performs a single exact-capacity allocation — `Vec::with_capacity(len)` + `push` is byte-identical (PR #706: 13 vs 13 allocs, 131,626 vs 131,626 bytes on the map path; 12 vs 12, 24,410 vs 24,410 on the fast path). Evidence protocol for such claims: a counting `GlobalAlloc` + `black_box` beats reading the loop shape, and the timing must agree in sign across shapes (PR #706 measured −4.4% and +4.3% in the same run = noise). Same class of unverified `perf(...)` PRs: #529 → #605 → #689 → #706 (and #737, closed with an empty diff). **`filter_map` is not `TrustedLen`**, so there the premise *does* hold a little: over 126 valid candidates, `filter_map(..).collect()` costs 132 allocs / 8 584 B against 127 allocs / 4 552 B for `with_capacity` + push (the remaining 126 allocations are the per-item `id.clone()`), while a `TrustedLen` `map(..).collect()` control costs 1 alloc. Pre-size when the iterator filters; measure before claiming either way. A second, independent measurement on `csm-retrieval::hybrid::merge_single_list` (`&[(String, f32)]` -> `Vec<(&str, f32)>`, no filter) confirmed it: 102 allocs / 6 090 bytes at n=100 and 1 002 / 61 890 at n=1000, **identical** with `with_capacity` + push — the allocations are the per-item `id.to_string()` downstream, so two PRs (#739, #740) that "removed reallocations" were no-ops.

## CI/CD Patterns
- **A dropped `#[test]` is invisible to every Rust sensor, so the detector has to be textual (2026-10-04, #822)**: `cli_each_subcommand_has_help` sat in `tests/cli_parity.rs` with no attribute, so `-- --list` registered 2 of the file's 3 test bodies and the suite stayed green. No compiler help exists: in a `--test` build rustc does not emit `dead_code` for a private `fn` whose only caller would be the harness, so clippy `--all-targets -D warnings` and `validate.sh`'s `cargo test --no-run` warning scan are both blind to it. `scripts/check-test-attributes.sh` (awk, column-0 `fn` whose attribute block registers nothing and whose name appears in no other non-comment line) now runs in `validate.sh` **with its negative fixture**, because a gate whose failure mode is untested can rot into a pass-for-the-wrong-reason check. Generalize: when a defect class has no compiler signal, the gate is a source scan plus a fixture that removes the thing and asserts the scan goes red.
- **gh multi-account (2026-09-08)**: keyring can hold `d-oit` + `d-o-hub`; after `gh auth switch` the CLI may still 401 on GraphQL. Verify identity with `gh api graphql -f query='{viewer{login}}'` and pin operations with `export GH_TOKEN=$(gh auth token -u d-o-hub)`. Dependabot silently ignores commands from accounts without write access — post `@dependabot rebase` as the repo owner.
- **Branch sync without `gh pr update-branch`** (subcommand absent in installed gh): `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/update-branch`.
- **Dependabot rebase ordering (2026-09-08)**: batch `@dependabot rebase` comments only AFTER all human PRs land (single rebase onto final main). Cargo.lock-group rebases lag workflow-file rebases (dependency resolution); drafts must be `gh pr ready` before any merge attempt.
- **CI queue wedge + rerun refusal (2026-09-08, twice)**: stuck `QUEUED` runs (0 in_progress, 0 completions, >1hr) block required checks; `gh run rerun` refuses them ("workflow file may be broken" — generic for never-started jobs). Remedy: `gh run cancel` all wedged runs, then re-trigger — empty-commit push for human PRs, `@dependabot recreate` for dependabot PRs (`rebase` replies "already up-to-date" and does nothing). Verify with `gh run list --status in_progress` > 0 and a fast workflow (Tooling Guard) completing.
- **Green checks on an empty diff prove nothing (2026-09-18)**: #737 showed 35/35 checks passing against a branch whose commit changed no files (`gh pr view <n> --json files` → `[]`), i.e. the matrix ran against tree == main. Verify the diff before the CI status when triaging: `gh pr view <n> --json files,additions,deletions` first, badges second.
- **A green run per SHA is not a green run per workflow (2026-10-03)**: `gh run list --branch <head>` returns *every* workflow for that commit. #812's `25a5948` had "Tooling Guard: success" and "CI: queued" at the same moment, and reading the first as the second made the PR look blocked-with-green-CI. Filter on `workflowName` (`--json workflowName,headSha,status,conclusion`), and when a merge is blocked, list the still-non-completed contexts from `statusCheckRollup` — that names the job, the run id, and therefore the workflow unambiguously.
- **`mergeStateStatus: BLOCKED` also means draft (2026-10-03)**: on this repo — `branches/main/protection` → 404 and a ruleset with `required_status_checks: null` — a draft PR reports `BLOCKED` with no visible reviewer requirement, and `mergeStateStatus` can flip to `CLEAN` while `gh pr merge` still refuses with *"Pull Request is still a draft"*. Include `isDraft` in the same `gh pr view --json` probe as `mergeable,mergeStateStatus,reviewDecision` before diagnosing protection rules.
- **Regenerate `llms.txt`/`llms-full.txt` in the same branch as the public-doc change (2026-10-03, #813)**: those files embed the public API surface and `Cargo.toml` text, so removing `impl Clone for McpHandler` or moving a cargo feature makes them stale. `scripts/check-llms-sync.sh` runs late inside `validate.sh`, so the drift surfaces as a *second* red on a head that was just fixed — `gh pr diff`-clean commits still fail the gate. Fix: `scripts/gen-llms-txt.sh` in the change branch, not a follow-up.
- **Unit-only coverage understates behavior coverage (2026-09-18)**: `cargo llvm-cov --lib` measured 68.39 % lines / 53.17 % branches on this workspace, while adding `--tests` (the 71 integration binaries, 538 of 1029 test functions) gave 74.33 % / 64.08 %. Report the target set with the number; branch coverage itself needs nightly (`-Z coverage-options=branch`), so the script falls back to line coverage elsewhere.
- **Concurrency on main**: `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}` — never cancel main pushes.
- **WASM dual-target**: `--target nodejs` for CI smoke, `--target web` for release. **Both must come from one script (2026-09-20)**: CI validated a `--dev --target nodejs` build (4 077 828 B) while the release published `--release --target web` + wasm-opt (656 657 B) and the size gate measured a raw `cargo build` output (1 133 971 B) — three artifacts, none of them the shipped one, so a release-only failure could not fail CI. `scripts/build-wasm.sh <dev-nodejs|dev-web|release-web>` is now the only build definition; use it in workflows, gates and local runs.
- **CI lint scope ≠ mandatory local gate scope (2026-09-23)**: ci.yml's `lint` job *and* `./scripts/validate.sh` both run clippy on the **root package only** (`cargo clippy --all-targets --all-features -- -D warnings`, no `--workspace`); the workspace-wide command exists only in `scripts/harness-check.sh` (`clippy` sensor, `--workspace` flag). That gap let two `manual_range_contains` errors in `csm-core-lib` unit tests go unnoticed by CI and by `validate.sh` while `harness-check.sh all` stayed red on main. When a lint is green in one gate but red in another, diff the **scope** before diffing the code.
- **A gate behind a path filter is a gate nobody hits (2026-09-23)**: the four `perf(...)` PRs in the #737/#739/#740/#754 class each carried a percentage claim with no Criterion output or flamegraph, and none of the measurement machinery fired on them — `benchmark-ci.yml` is paths-filtered, `bench-*` jobs need `detect-changes`. Fail-closed presence checks belong in the always-on `commitlint` job (title/body through env vars, never shell interpolation); keep real measurement gates (`benchmark-ci.yml` thresholds, `scripts/bench-baseline.sh compare`) separate. A presence/shape check deliberately does **not** validate provenance or assert improvement — a hardware-sensitive speed threshold on shared runners fails honest PRs and passes the ones that never ran a bench.
- **Python `strip` gotchas (2026-09-23)**: a string set ending in `\\`+`"` (`"*_\`~#<>|\\"`) drops the backslash entirely — it escapes the closing quote instead of adding the character; build sets with `chr(92)` when in doubt. And `.strip()` is non-greedy across passes: `"` + backtick + `.strip(decorators)` leaves the backtick when a period follows it, so strip decorators and punctuation in **one** call before matching tokens like `target/criterion/...`.
- **A gate that regenerates its subject cannot detect drift (2026-09-27)**: `scripts/validate.sh` ran `scripts/gen-llms-txt.sh`, which rewrote `llms.txt`/`llms-full.txt` in the working tree and exited 0 whatever the committed copies said — so CI stayed green while the committed files still listed `opentelemetry 0.27` / `rmcp 1.7` across the #728/#729 bumps (last regenerated at #714). The check shape is snapshot → regenerate → `cmp` → fail naming each stale file (`scripts/check-llms-sync.sh`); missing inputs must fail instead of becoming an empty baseline, and generator failure must propagate its exit code rather than be reported as success. Fixture tests (`scripts/test-llms-sync.sh`, stub generator, no Cargo) cover those branches. Never hand-edit the generated files — fix the generator or its inputs.
- **Cargo.lock atomicity**: always commit lockfile with Cargo.toml changes or `--locked` jobs fail.
- **Node 20 deprecation**: use Node 24-capable actions (`checkout@v5+`, `rust-cache@v2.9.1+`).
- **Miri timeout**: 60 min minimum for ~220 tests.
- **Action pinning**: `git ls-remote --tags <url>` for exact SHA.
- **Native arm64 runners**: cross-compiled NEON is not tested NEON; `ubuntu-24.04-arm` runs `cargo test -p csm-core-lib` on real aarch64 (PR #599).
- **YAML plain-scalar trap**: `: ` inside single quotes still terminates a plain scalar — double-quote the whole `run:` value.
- **Benchmark under load**: absolute ns shift with load (37.7 → 54.5 ns idle→loaded). Report ratios under identical conditions, never bare absolutes.
- **Stale-binary detection**: cargo silently reuses builds across worktrees sharing a target dir; a result contradicting theory means the wrong binary ran — grep the log for `Compiling csm-memory (path)` before trusting a number.
- **Forced clean A/B**: `touch` changed sources per side, grep the linked lib path, interleave A/B/A/B, record `loadavg`, discard runs during spikes (excluded 281/301 runs at loadavg 2.7).
- **Deterministic test graphs**: hash-based pseudo-random edges (not ring/wrap successors) model association graphs realistically and reproduce across branches — ring graphs understated BFS wins ~7×.
- **A memory model has a valid range, not a slope (2026-09-21)**: the bytes-per-concept fit was linear within 0.29 % at 100k but under-predicted the measured 500k point by 15.6 % (2.80 GB actual vs 2.36 GB predicted) — publish the measured points and the fit's domain; a single slope extrapolated to 10M is a lower bound, not a claim.
- **Storage medium dominates latency gates (2026-09-11)**: `local_persistence_roundtrip_p50_under_20ms` measured 1.2 ms on RAM-backed `/tmp` and 13.9 ms on ext4 for the same revision, and 24.47 ms on the CI runner — main run 34610334012 failed the 20 ms ceiling with no code change. The CI `test` job now mounts tmpfs at `/tmp` so the gate measures a fixed medium on the path the suite already uses (the path validator accepts absolute paths only under cwd or `/tmp`, so `TMPDIR=/dev/shm` breaks export/import tests). A "20x regression" that appears only in CI is usually a different filesystem, not slower code.
- **A mitigation applied to one job is not applied to the second job running the same suite (2026-09-23)**: ci.yml's `lint` job finishes with `bash scripts/validate.sh`, which itself runs `cargo test --all-targets --all-features` — the same `local_persistence_roundtrip_p50_under_20ms` gate as the `test` job, but `lint` had no tmpfs mount, so run 35846414646 failed it with zero Rust diff (the `lint` step before it, Format/Clippy/Skill-format, all passed). When a gate fails with no code change, check whether **every** job that executes the suite carries the mitigation, not just the job named after it.
- **Scheduled-workflow blindness (2026-09-12)**: "latest CI green" checks that only look at ci.yml hide weeks-old reds — fuzz.yml's scheduled full run failed six consecutive Sundays (08-02 → 09-06) because the nix devshell pinned a stable toolchain while `cargo fuzz` needs nightly (`-Zsanitizer=address`), and PR-time fuzz-short is paths-filtered so normal development never sees the job. Sweep every workflow's *latest* main run. Fix shape: drop nix from the fuzz jobs, reuse ci.yml's pinned `setup-rust-toolchain` action with `toolchain: nightly` + `cargo install cargo-fuzz --locked` (PR #690); validate via `workflow_dispatch` (run 34709772141 green) instead of waiting for the next Sunday.
- **Release wait-for-ci ceiling drift (2026-09-12; third occurrence 2026-09-24)**: CI duration grows with the suite; the Release guardrail's `MAX_WAIT=1800` expired in 8 runs (09-07 → 09-09) while CI itself was green every time. Raised to 2700s with job `timeout-minutes: 55` (PR #690). It drifted again on run 36031855839: the wait-for-ci job sat for the full 2700s while main CI on the same SHA (`31f793f`) stayed `queued` for ~40 min on a saturated runner pool and only started at ~2700s — the polling loop could not distinguish "CI is slow" from "CI has not been scheduled", and its queue-starvation recovery (`gh run rerun` at `QUEUE_THRESHOLD=600`) cannot help because a *queued* run has nothing to re-trigger. Publishing steps were correctly `skipped`, so no release leaked. Third occurrence ⇒ stop raising the ceiling and migrate `wait-for-ci` to a `workflow_run`-triggered design (the earlier prescribed fix), which is event-driven and has no ceiling to drift.
- **Polling a gate is a ceiling you will raise forever; migrate to the event (2026-09-30)**: `release.yml`'s `wait-for-ci` ceiling went 1800 → 2700s and was abandoned a third time on run 36031855839 (main CI sat `queued` ~40 min on a saturated runner pool) because a poll cannot distinguish "CI is slow" from "CI was never scheduled" — and a queued run gives `gh run rerun` nothing to do. The fix is not a bigger `MAX_WAIT`: the release now triggers on the *completion of the CI workflow* (`workflow_run` on `ci.yml`, `types: [completed]`, `branches: [main]`), releases exactly `github.event.workflow_run.head_sha` (the commit whose CI passed) instead of whatever `github.sha` points at when the job starts, and gates the job on `conclusion == 'success'` plus `head_repository == github.repository`. A manual dispatch keeps the fail-closed rule with one query instead of a 45-minute loop. Rule: when a polling gate can only be kept alive by raising its ceiling, replace the trigger with the completion event of the thing you were waiting on. Verified post-merge the same day (PR #796): CI on the merge SHA finished `success` and release run 36746741481 fired with `event: workflow_run` (`validate` success, every publish job `skipped` because tag `v0.3.8` exists, no `push`-triggered run for that SHA), and the dispatch path passed its single-query guard — log line `CI on 8c1f864d…: status=completed conclusion=success`, then `Tag v0.3.8 already exists; skipping release.` (run 36746882951).
- **setup-rust-toolchain v2.0.0 deny-warnings cascade (2026-09-13)**: v2.0.0 replaced the `RUSTFLAGS="-D warnings"` default with cargo *config* `CARGO_BUILD_WARNINGS=deny`. Builds that set their own `RUSTFLAGS` (cargo-fuzz `--cfg fuzzing`, `cargo miri setup` sysroot) previously *replaced* the action's env and escaped deny — config-level deny cannot be escaped, so both jobs went red on warnings that are inherent to those tools (cargo-fuzz's snake_case `[[bin]]` names trip the kebab-case lint; miri's generated sysroot emits `unused dependency sysroot`). Fix: job-level `CARGO_BUILD_WARNINGS=allow`. Facts: valid levels are `warn`/`allow`/`deny` — **`none` is rejected** ("could not load config key", run 34753920773); the key is respected only by cargo ≥ 1.97, so stable-toolchain jobs ignore it. Neither affected job runs on ordinary PR CI (fuzz paths-filter; miri/mutation gated on `rust_src`), which is why #696 shipped green — after merging major bumps of setup-* actions, `gh workflow run` the gated workflows manually.
- **Dependabot double scope (2026-09-17)**: `commit-message.prefix: "chore(deps)"` plus `include: "scope"` yields `chore(deps)(deps): …`, which fails `scope-enum` wherever a title is linted. Set `prefix` to the bare type (`chore`, `ci`) and let `include: "scope"` add `(deps)`.
- **PR-title checks keyed on `github.actor` misfire after `update-branch` (2026-09-17)**: the guard `github.actor != 'dependabot[bot]'` skips Dependabot PRs only while the bot is the last actor; a maintainer running `PUT /pulls/<n>/update-branch` makes `github.actor` the maintainer, so the bot's title gets linted and fails. Key the exemption on `github.event.pull_request.user.login`.
- **`lock file needs to be updated but --locked was passed` on a bot PR (2026-09-17)**: this is a stale base, not a real failure — the branch predates a lockfile-affecting merge on main (job dies in ~20 s, #724). `PUT /pulls/<n>/update-branch` and re-run; do not touch the dependency.
- **Parallel lib tests race on process-global env (2026-09-13)**: `cargo test --lib` runs test threads concurrently; `unsafe { std::env::set_var/remove_var }` pairs in different tests of the same binary interleave, so one test's `remove_var` lands between another's `set_var` and the code under test. The openai embedding tests "tolerated" the race by accepting either outcome; the voyage tests asserted strictly and failed intermittently. Fix: one `static ENV_TEST_LOCK: Mutex<()>` held across the whole set→call→remove span (PR #700). Don't write SAFETY comments claiming single-threadedness under cargo's default test harness.

- **A validator nobody invokes is dead weight, and a "keep in sync" comment is not a check (2026-09-30, wave-32 exit pass)**: `scripts/validate-workflows.sh`, `validate-git-hooks.sh` and `validate-links.sh` have zero callers in `validate.sh`/CI/hooks; `scripts/test-llms-sync.sh` and `test-version-sync.sh` exist as negative fixtures but no gate runs them, so their own regressions would go unnoticed; and `ci.yml`'s `test-workspace-crates` matrix (`ci.yml:202-241`) is a hand-written crate list guarded only by a comment, so a new `crates/*` member silently skips CI. ## Feature-Gating / Disabled-Capability Contracts (ADR-0094)
- **No false success on disabled features**: record config and reject at `build()` with `UnsupportedOperation`; fallback facades return `Err`, never `Ok`/empty. Idempotent no-ops (`without_persistence()` when already off → `self`) are fine.
- **Gate tests, don't inherit fake success**: every test exercising a disabled feature needs per-test `#[cfg(feature = "persistence")]` or a file gate — CI's `--all-features` and lean matrix never compiled un-gated tests. Verify with full `cargo test --no-default-features` (all targets) + `required-features` on examples.
- **Disk-full ≠ test failure**: `cc: No space left on device` under `--all-features` is environmental; `CARGO_PROFILE_TEST_DEBUG=0` shrinks linked test binaries.
- **Mutation note**: `#[cfg(feature)]` on a test also gates its doc — keep one rationale comment per assert.
- **A target-independent feature leaks host-only deps into the wasm32 check (2026-10-03, #813)**: moving `tokio/signal` from the `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]` table onto the `cli` feature broke `cargo check --target wasm32-unknown-unknown --features wasm` with 48 `mio` errors — `cli` is in the **default** feature set, so the wasm32 build turns it on and pulls `tokio → mio/net`, which has no backend when both `cfg(unix)` and `cfg(windows)` are false. The `wasm` CI job stayed green the whole time because it builds `-p csm-wasm` with `default-features = false`; only `validate.sh`'s wasm stage exercises the default-set leak. Gate: after any dependency-feature change run the wasm32 default-set check, and never delete a rationale comment that documents this hazard (the one that was deleted predicted the failure verbatim).

- **A new config knob is only proven when a test observes its *effect* (2026-10-03, #817)**: `enable_ttl_cleanup_in_long_running_commands` threads a user `u64` through CLI and MCP into a background task, and every intermediate hop (`McpConfig` field → handler builder → framework field) is assertable without the reaper ever running. The discriminating assertion is a *raw stored-row count*: `fw.singularity().read().await.len("_default")` going 1 → 0 with no `purge_expired` call proves the task deleted something — probe-time reads filter expired entries out, so any query-based assert would pass while nothing was ever removed. Put that effect test at the shared constructor (`create_framework_with_ttl`, which both entry points call), then cover each path's *own* hop separately — the MCP test asserts `fw.cleanup.is_some()` because the last hop (config → handler → framework) is what is unique to MCP — and add the off-state pair: `cleanup.is_none()` **plus** a provably `is_expired()` row still in `len()`, so "off" is measured the same way "on" is. State the default's meaning in the test name too: `0` means off, so an upgrade cannot silently start deleting user data.
- **An unbounded `u64` config input is not automatically a panic (2026-10-03, #817)**: `--ttl-cleanup-interval` is a user-controlled `u64` handed to `tokio::time::interval(period)`, and the reflex was to clamp it like the TTL seconds. Read the callee instead: tokio 1.53.1 resolves an out-of-range period via `checked_add(period).unwrap_or_else(Instant::far_future)` (`src/time/interval.rs:478`), so the deadline saturates and the reaper simply never fires. Prove the boundary against the built binary (`csm watch --ttl-cleanup-interval 18446744073709551615` exits clean) and record *why* no clamp is needed, rather than adding dead validation that a later reader must re-derive.

## Mutation Testing
- **A queued `test(...)` action is mispriced until you check that the condition can be *produced* (2026-10-03, pre-audit of the next two queue items)**: `add_persistence_failure_path_test` and `add_query_count_regression_test` both read as "add a test", and both are `fix(...)` work. `Persistence` is a concrete struct with a `pub(crate) db: Arc<Database>` (`crates/csm-persistence/src/persistence.rs:14`), there is no `trait Persistence` and no Failing/Mock/Fault impl anywhere, and the only error-returning impl is the feature-disabled stub (`src/lib.rs:93` `unsupported()`) — which cannot reach the code, because `build()` itself rejects a configured DB when `persistence` is off (`src/framework_builder.rs:399-402`, asserted by `tests/persistence_disabled.rs:15`). Likewise `grep -rn "query_count|num_queries"` returns 0 hits: pinning a query count needs instrumentation before it needs an assertion. Three greps reprice the PR, change its type, and tell the reviewer what is actually landing. Second-order finding from the same pass: check *which profile compiles the new test* — `scripts/mutation_test.sh:142` passes `--lib -p csm-retrieval -p chaotic_semantic_memory`, so a `tests/` integration test or a `csm-persistence` unit test is invisible to the mutation job, which is how #817's first head went red for an entirely different reason.
- **A line no transport can reach is unkillable, not merely uncovered (2026-10-03, #817)**: while writing `scripts/mutation_test.sh` exclusion comments I claimed `serve`'s ADR-0099 shutdown hop "is asserted" by `tests/mcp_sse_integration.rs`. It is not, and it cannot be: `run_sse_server` awaits `axum::serve(listener, app)` with no `with_graceful_shutdown`, and axum 0.7.9's `Serve::into_future` is an infinite accept loop (`serve.rs:205-240`; `tcp_accept` returns `Option` and never propagates `Err`, `:474-496`), so `serve` never returns and `src/mcp/server.rs:98` is dead on the SSE path (it *is* live on Stdio, where rmcp's `Waiting::waiting` resolves on stdin EOF). - **`--in-diff` on post-fix tree**: generate the diff after the fix is staged, not before.

## Module-Specific
- **`csm mcp serve` logs nothing at the operator level, so prove signal behaviour by exit code (2026-10-04, #821)**: the serve path installs no tracing subscriber (only `src/observability/` does), so `RUST_LOG=info` yields an empty log and grepping for the `info!("Received Ctrl+C…")` line proves nothing either way. What *is* observable is the wait status: after rebasing the merged tree, `./target/debug/csm mcp serve --transport sse` + `kill -INT` → **exit 0** (transport resolved, `serve` returned, ADR-0099 hop ran) and `kill -TERM` → **exit 143** (128+15, default disposition — the disclosed SIGINT-only limitation, measured instead of asserted). Build the check as a script that waits on the PID and prints `$?`; and keep `set -uo pipefail` in mind when the last command is `grep -c` (no match ⇒ exit 1 ⇒ the harness reports failure for a run that proved its point).
- **Derived negative knowledge needs the same revision contract as derived positive data (2026-10-01, audit F1)**: the absence short-circuit stored "this query matched nothing" with no notion of *when*, so it outlived the content that made it true and kept suppressing a query after matching concepts existed. Stamp such records with the content revision they were observed at — the namespace revision every durable mutation already bumps (ADR-0093) — and compare on read instead of enumerating invalidation points on the write path: no insert-path cost, and no mutation path anyone can forget. Three details decide whether it works: stamp the revision the probe **observed before** the work (a revision re-read afterwards can be newer than what was actually seen, which would mis-attribute the observation to newer content); restart the attempt counter when the revision changed, since attempts against older content must not accumulate toward the current threshold; and fail closed when the revision cannot be read, while a failed *write*-path read should stamp a value that can never match. Verify a schema change like this by parking a full database at the previous schema version — a fresh database exercises creation, not the upgrade.
- **Reservoir**: CSR for >2000 nodes. Partitioned updates must preserve momentum.
- **Similarity**: Derive cosine from hamming (`1.0 - dist/5120.0`) for bipolar hvecs.
- **Top-K**: `select_nth_unstable_by` for O(N) partial sort.
- **WASM**: Gate rayon/IO with `#[cfg(not(target_arch = "wasm32"))]`.
- **Persistence**: `csm_`-prefixed tables. Update all surfaces (single, batch, export, WASM) when adding fields.
- **WASM bincode configs must match (fixed 2026-09-17)**: `WasmFramework::exportToBytes` previously wrote with `bincode::serialize` (legacy fixed-width config) while `importFromBytes` read with `bincode::DefaultOptions` (varint), causing browser export→import round trips to fail with `string is not valid utf8`. Aligned `exportToBytes` to use `DefaultOptions::new().with_limit(MAX_IMPORT_SIZE)` matching `importFromBytes` and native `export_binary`/`import_binary`; added round-trip assertion to `wasm/test.js`.
- **Floats**: Never `partial_cmp().unwrap()` — NaN panics. Use `total_cmp()`.

Check the sign rule of the operator against the documented interval before accepting a numeric claim; no simulation was needed to refute it.
- **Chaos-bench parameters can make a benchmark measure the opposite of its stated cause (2026-10-02)**: a bench seeded with `c` outside the main cardioid escapes, so the divergence-fold libcall sits on the hot path, while the write-up claimed seeds near the boundary. Membership in the intended invariant set is a property of the bench's *arguments*, not of the code under test — the #800 lesson again, one layer down.
- **Measure a PR's own baseline before accepting its perf pair (2026-10-02)**: #808 claimed 287.6 ns -> 141.5 ns; copying its bench into a worktree on `origin/main` measured 89.5 ns vs 113.3 ns, i.e. a 26% regression with the sign inverted. A PR that adds its own `bench_function` for the changed path is *checkable* — build a worktree at the base SHA, drop in the same bench file, run both arms on the same host. `git worktree add /tmp/wt-base origin/main` plus one `cargo bench` is cheaper than any amount of code reading, and it is the only way to catch a number that is true for the author's toolchain and false for the one the crate ships with (that PR's premise cited rustc 1.98.1 against a 1.88 MSRV).
- **`#[target_feature]` SIMD writing into a stack buffer can lose to the scalar loop it replaced (2026-10-02)**: disassembling the "vectorized" `xor` showed the added dispatch pays a `memset` of the 1,280-byte destination (the zeroed stack temporary must survive the `MaybeUninit` kernel call), a `memcpy` out of it, and an out-of-line `call` to the kernel — a `target_feature` fn cannot inline into a caller lacking the feature. The data crosses the stack three times instead of once, which is why 1,280 bytes of XOR got slower. When a hand-written kernel is claimed faster, read the asm for `memset`/`memcpy`/`call` before reading the benchmark; a vectorized kernel only wins when it writes straight to the destination.

- **Dropping the read end of a child's stderr makes the child panic with exit 101 (2026-10-04)**: the first version of `tests/cli_shutdown_signal.rs` did `child.stderr.take()` → `BufReader::lines()` → `.any(|l| l.contains("Press Ctrl+C"))`, which stops reading at the ready line and closes the pipe when the reader drops. The child's *next* `eprintln!("Interrupted.")` then hits EPIPE and `eprintln!` panics, so the test observed `ExitStatus(unix_wait_status(25856))` — exit 101 — and blamed the production signal handler for a bug in the harness. Two rules fall out: drain a subprocess's stderr on a dedicated thread for the child's whole lifetime (a never-read pipe also deadlocks a chatty child, which reads as a hang rather than a failure), and never let a readiness check discard the output that would explain a premature death. The fix also cut the debug loop from "guess" to "the panic message was right there".
- **Assert the OS-level effect when the in-process test cannot see the defect (2026-10-04)**: SIGTERM was missing for the entire life of the SSE shutdown work and `src/mcp/server_tests.rs` stayed green, because it resolves a *synthetic* future to prove the plumbing. A handler that is written but never registered is indistinguishable from one that is registered, from inside the process. The exit status is the discriminator: cooperative stop → `0`, default disposition → `signal: Some(15)` / shell `143`. When a test's oracle is a config echo or an injected future rather than an OS observable, ask what state it literally cannot distinguish.
- **Re-verify a queued note's stated obstacle before pricing the work (2026-10-04)**: `cover_sigterm_in_server_shutdown` carried a warning that a SIGTERM listener had to respect the `signal`/wasm32 target gate at `Cargo.toml:197-202`. `Cargo.toml:202` already listed `"signal"`. The note was written against an older tree, and had the implementer trusted it, the action would have been scoped as a dependency change plus a feature-gate puzzle. A stale note is not merely imprecise — it can invent the cost of a task. Grep the constraint before accepting it.
- **"O(1)" in a perf claim is checkable from the return type alone (2026-10-04)**: PR #819 advertised converting identity rotations into "an O(1) register/stack move". `HVec10240` is `[u128; 80]` — 1280 bytes, returned by value, so `return *self;` copies 1280 bytes. No benchmark was needed to refute the shape of the claim, only `grep -n 'pub struct HVec10240' -A2` plus the DIMENSION constant. Read the type before the numbers; a by-value large-struct return cannot be O(1), and the same PR's `zero-initialization` half was also untouched because `let mut result = [0u128; 80];` sits *before* the added branch.
- **A YAML world-state file can self-contradict with no duplicate key (2026-10-04)**: the hygiene rule that `action_last_completed` appears exactly once caught nothing here — `plans/GOAP_STATE.md` had `sse_transport_has_exit_path: false` while the comment under `queued_actions_count` in the same file recorded #821 completing exactly that. Duplicate-key checking validates *form*, not *consistency*. Reconcile flag-vs-narrative in the same pass, and treat a `false` flag on an action the same file calls completed as a bug report against the file.
- **An empty issue list is not evidence of a clean backlog (2026-10-04)**: `gh issue list --state open` returned `[]` while `plans/ACTIONS.md` held 10 verified-missing actions. The repo's own workflow treats `plans/` as canonical, so nothing forced a mapping and the backlog was invisible to any consumer of GitHub — including a future session that checked the tracker and stopped there. Bidirectional mapping is the fix: `github_issue:` on every action, and re-derive the count with `grep -c '^    github_issue:' plans/ACTIONS.md` rather than asserting it.

- **A duplicate PR is a coverage audit, not just noise (2026-10-05)**: draft #834 implemented the same SIGTERM primitive as #836 independently — and its tests drove `csm mcp serve --transport sse`, which #836 did not. The move was not to argue about which copy lands, nor to merge both: read what the other branch *tests* that yours does not, fold that one dimension in (`c62f2ce`), and let your branch strictly dominate. Two agents converging on the same design is also the cheapest possible confirmation the fix is the obvious one; say that out loud in the roast while listing the six places the duplicate is weaker (unbounded `child.wait()`, fixed 200/300 ms readiness sleeps, no `--database`, a vacuous async test, a widened public API, `recv()`'s `Option` discarded).
- **`let _fut = async_fn();` is a compile check wearing a `#[test]` (2026-10-05)**: #834 shipped `shutdown_signal_compiles`, whose whole body constructs the future and drops it. Rust `async fn` is lazy, so nothing runs — no arm is polled, no handler is installed — and the only thing proven is that the crate already compiles, which the build proves for free. It still raises the test count by 1. `scripts/check-test-attributes.sh` cannot catch this: it verifies that test-shaped functions are *registered*, not that they *do* anything. Ask of any async test: is the future awaited, or merely named?
- **A subprocess signal test needs a deadline on the wait, not just on the spawn (2026-10-05)**: `child.wait()` after `kill -TERM` is the shape that hides the very defect the test exists to catch — if the cooperative stop regresses, the process never exits and the test hangs until the CI job times out, which reads as infrastructure, not as a red assertion. Bound it: poll `try_wait()`, fail at a deadline comfortably above the production bound (`EXIT_DEADLINE` 15 s vs the 5 s internal `shutdown()`), kill-and-report on expiry. Same reason fixed `sleep(200ms)` "give it a moment to install handlers" is the wrong synchronisation: the child prints a line at exactly the moment in question, so wait for that line.
- **Never spawn `csm` in a test without `--database` (2026-10-05)**: with no path, `src/cli/args.rs:20` falls back to git-local storage, so a bare `csm watch`/`csm mcp serve` in a test creates and writes `.git/memory-index/csm.db` inside the checkout it is running in — non-hermetic, and it can change what a later `git status` in the same job reports. Tests in this repo pass an explicit `tempfile` path for exactly this reason; a PR that forgot it was caught by reading `args.rs`, not by a red CI run, because CI never tells you a test polluted the worktree.
- **`--exclude-re` matches the mutant description, not an item path — and I got it backwards twice (2026-10-05)**: I first wrote that #834's `--exclude-re "replace shutdown_signal"` was inert "because no Rust path contains the word replace". Wrong on both halves. Measured with counts on `cargo-mutants 27.1.0` against `src/shutdown.rs` (baseline 3 mutants): `"replace operator_shutdown"` → 2, `"sigterm"` → 2, `"shutdown::"` → 3, control `"zzz_no_match"` → 3. So the pattern set **is** the description text (`replace <fn> with ()`) and module-qualified paths are what silently match nothing. The repo's own `--exclude-re "McpHandler::"` is alive by the same rule (`src/mcp/handler.rs` 12 → 8). Full writeup: `.agents/skills/pr-roast-triage/references/subprocess-and-claim-rubric.md`.
- **A `tail`-truncated probe is not an experiment (2026-10-05)**: the false claim above came from `cargo mutants --list | tail -N` — the truncated view showed two mutants where three existed, which read as "nothing excluded". Two rules: count with `| grep -c` (or `wc -l`) instead of eyeballing a tail, and always run a control that must *not* change the result plus a positive that must. Related trap in the same session: `(cargo mutants --help | grep -A2 -- --exclude || echo "NOT installed")` printed "NOT installed" because **grep found nothing**, not because the binary was missing — it was at `~/.cargo/bin/cargo-mutants` the whole time, and that phantom constraint then leaked into a learnings entry and a skill file before anyone checked. A fallback `echo` behind a pipeline reports your pipeline's exit status, never the tool's state.
- **A wrapper's exit code is not the gate's exit code, and I re-made that mistake in the same session I documented it (2026-10-05)**: `timeout 600 ./scripts/harness-check.sh all > f 2>&1; echo "RC=$?"; tail -25 f` reported *"completed (exit code 0)"* — that 0 is `tail`'s. The harness had actually been killed by the 600 s timeout mid-`cargo check`, with no summary line at all. The tell was in the file itself: the last line was a `Checking …` row, not a verdict. Two habits, both mechanical: run the gate alone with `; echo "GATE_RC=$?" >> file` **as the final statement inside the redirect target**, and treat an output that ends mid-build as *unknown*, never as *passed*. This is the second occurrence of the same error class (first recorded 2026-09-23 / 2026-10-04 for `validate.sh`), which means the rule was written but not yet turned into a habit — a documented lesson that keeps recurring is a lesson that needs a script, not a rewording.
- **A process-level test cannot feed a `--lib`-only mutation gate (2026-10-05)**: PR #836 shipped the SIGTERM fix with a subprocess test that asserts the real observable (exit 0 vs `unix_wait_status(15)`), and CI still failed at `mutation score 0.0000%` — all three `src/shutdown.rs` mutants survived, because `scripts/mutation_test.sh:142` runs the fast profile as `cargo mutants --lib -p csm-retrieval -p chaotic_semantic_memory` and `tests/**` is never built there. Sharpness is not reachability: a test that would catch the regression perfectly cannot kill a mutant the harness never runs it against. Before claiming coverage of a mutation-gated change, read which targets the profile executes, and put an assertion the profile *can* see in the same target as the mutated code (here: `src/shutdown_tests.rs`, one pending-check per arm, each mutant reproduced individually). Corollary worth keeping: I had written this exact limitation up as a flaw in a competing PR (#834's `--exclude` on a file whose tests the profile also could not see) and still let it pass unexamined on my own branch — auditing the rule's application to *your* diff is a separate step from knowing the rule.
- **Do not `raise()` a process-wide signal inside `cargo test --lib` to prove a handler works (2026-10-05)**: the correct code resolves the future, but a mutant that skips the registration leaves the default disposition in place and the signal kills the entire test binary — the gate then reports a crash, and every other test in the process is collateral. The safe lib-level property is the negative one ("no signal, no resolution", which every `replace <fn> with ()` mutant violates); the positive one needs process isolation, a bounded wait, and one child per signal.
- **A failed probe prints an empty result, and an empty result is not a measurement (2026-10-05)**: third instance of the same error class in one session. `cargo mutants --list --lib -p chaotic_semantic_memory` died on `error: unexpected argument '--lib'` (cargo-mutants 27.1.0 wants `--list -p <pkg>`, with cargo test args after `--`), leaving stdout empty — and `grep -c 'shutdown_tests.rs'` on that empty file returned `0`, which reads exactly like "the test file generates no mutants". The conclusion happened to be true, but it was reached from a dead instrument; `LIST_RC=1` was the only thing distinguishing it from evidence. Same shape as the `tail`-truncated `--list` that produced the retracted `--exclude-re` claim and the `grep || echo "NOT installed"` that invented a missing dependency. Mechanical rule: **assert the probe succeeded before interpreting its output** — capture RC first (`cmd > out 2> err; rc=$?`), check `rc`, only then count; and always include one query whose answer you already know (total mutant count, a file known to exist) so a silent-zero instrument cannot pass as a measurement.
- **A script that has never been invoked has two properties nobody tested (2026-10-05, #829)**: `scripts/test-version-sync.sh` passed from the repo root (RC=0, 4 cases) and failed from anywhere else with `cp: cannot stat 'scripts/verify-version-sync.sh'` (RC=1 measured from `/tmp`) because it resolved its own subject through the CWD; it was also committed **mode 664**, so `validate.sh`'s `-x` guards would have skipped it as "not installed" and reported nothing wrong. - **"No checks" and "all checks done" are the same empty query result (2026-10-05)**: a monitor watching PR #838 fired `SETTLED state=UNKNOWN checks_pending=0 failures=0` — not because CI went green but because the PR had **merged** and the branch was deleted, so `gh pr checks` and `gh pr view --json mergeStateStatus` both had nothing to report.
